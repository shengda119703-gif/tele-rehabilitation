# Qt styling architecture

## Recommended stack

```text
FluentThemeManager
├─ TokenRepository
│  ├─ official light/dark snapshot
│  ├─ Qt semantic aliases
│  └─ optional shell aliases
├─ QPalette builder
├─ application QSS renderer
├─ dynamic-property helpers
└─ theme/system-preference signals
```

Use one authoritative theme manager. Widgets should not load JSON or decide light versus dark independently.

## `QPalette`: broad semantic defaults

Use an application palette for roles Qt and native styles already understand:

- Window / WindowText;
- Base / AlternateBase / Text / PlaceholderText;
- Button / ButtonText;
- Highlight / HighlightedText;
- Link / LinkVisited;
- ToolTipBase / ToolTipText;
- Active, Inactive, and Disabled color groups.

Benefits:

- standard widgets and unstyled areas inherit sensible defaults;
- disabled colors are centralized;
- item selection and text editors have a coherent base;
- high-contrast mode can begin from the system palette.

Do not expect `QPalette` alone to reproduce Fluent control borders, radius, padding, or all states.

## Application-wide generated QSS

Use a single generated style sheet for component visuals. Store a source template with semantic placeholders:

```css
QPushButton[fluentAppearance="primary"] {
    background-color: @{brand_background};
    color: @{text_on_brand};
    border: 1px solid transparent;
    border-radius: @{radius_medium};
}
```

Render it through the theme manager and fail on unknown placeholders. Do not silently leave unresolved tokens in production QSS.

Apply the rendered QSS at `QApplication` or a deliberate top-level scope. Avoid applying different giant sheets to multiple subtrees.

## Dynamic properties

Dynamic properties express intent without subclassing every control:

```python
set_fluent_property(save_button, "fluentAppearance", "primary")
set_fluent_property(delete_button, "fluentAppearance", "danger")
set_fluent_property(card, "fluentRole", "card")
set_fluent_property(field, "fluentInvalid", has_error)
```

After changing a property, repolish that widget:

```python
style = widget.style()
style.unpolish(widget)
style.polish(widget)
widget.update()
```

Do not repolish the entire application for a single item state change.

Use Qt pseudo-states where they already model the state correctly:

```text
:hover
:pressed
:checked
:selected
:disabled
:focus
:read-only
```

Use dynamic properties for semantic roles Qt does not know, such as severity or appearance.

## Local style-sheet exceptions

A local style sheet is acceptable only when all are true:

- the widget is a self-contained third-party or embedded boundary;
- application QSS cannot target it safely;
- the local sheet uses semantic values generated by the theme manager;
- every applicable state is covered;
- the exception is documented.

Never use local QSS as a quick fix for spacing or font weight.

## `QProxyStyle`

Use a proxy style for narrow behavior or metrics that QSS cannot express reliably:

- icon sizes and pixel metrics;
- focus rendering;
- checkbox/radio indicator geometry;
- style hints;
- selected native subcontrol behavior.

Rules:

- wrap the current application style rather than assuming one platform style;
- override the smallest possible set of methods;
- retain the base style for all unhandled controls;
- test Windows, macOS, and Linux targets separately;
- do not use a proxy style to repaint the entire toolkit from scratch.

## Item views and delegates

Use model/view correctly. Do not replace a `QTableView` with a grid of labels to gain visual control.

Use QSS for:

- background, selection, alternate rows;
- header base style;
- borders and padding where supported.

Use delegates for:

- badges, progress, multi-part cells;
- conditional foregrounds/icons;
- custom focus/selection geometry;
- content whose layout cannot be expressed through QSS.

Delegate rules:

- respect `QStyle.State_Selected`, `State_HasFocus`, disabled state, and active/inactive window;
- derive colors from semantic aliases or the option palette;
- use device-independent metrics;
- preserve editor creation and accessibility;
- do not mutate the model while painting.

## Theme-manager lifecycle

The manager should:

1. load and validate token maps once;
2. determine the requested mode: system, light, dark, or high contrast;
3. resolve semantic aliases;
4. build a palette;
5. render application QSS;
6. apply font/palette/QSS in a controlled order;
7. emit a theme-changed signal;
8. allow custom-painted widgets to update cached colors.

System-following mode should react to `QStyleHints.colorSchemeChanged`. Qt updates its default palette around the scheme change; application-specific colors should be refreshed after palette-change events rather than assuming the old palette is already replaced.

Where available, inspect `QStyleHints.accessibility().contrastPreference()` and its change signal. Feature-detect this API to keep older PySide6 versions usable.

## Font handling

Do not bundle font files with the skill.

Preferred approach:

- begin with `QFontDatabase.systemFont(QFontDatabase.GeneralFont)`;
- prefer Segoe UI Variable/Segoe UI on Windows if installed;
- preserve platform fallback elsewhere;
- define semantic roles through cloned `QFont` objects;
- use pixel or point sizing consistently within the project;
- account for user scaling and avoid clipping with `QFontMetrics`.

A fixed 14 px body size may match Fluent visually but can override a user’s larger system font. Projects must decide whether exact design sizing or system text scaling takes precedence, and accessibility mode should favor the user.

## Icons

Use SVG resources and a central icon service.

The icon service should support:

- regular and filled/selected variants;
- semantic color tinting where assets permit;
- 16/20/24 px logical sizes;
- disabled and high-contrast variants;
- resource-path validation;
- cache invalidation on theme change.

Do not recolor detailed multicolor illustrations as if they were symbolic icons.

For QSS subcontrols, Qt does not reliably propagate the widget `color` into an
SVG's `currentColor`. Render symbolic source SVGs into a theme-manager-owned
temporary cache using semantic foreground aliases, then inject their absolute
paths while rendering the application QSS. Use color-dependent filenames so a
theme change cannot reuse a stale Qt image cache entry. Keep resolved colors
out of both the source SVG and QSS template.

## Shadows

Qt’s standard drop-shadow effect is one-layer and can be expensive.

- avoid shadows on every card;
- prefer 1 px semantic borders for persistent surfaces;
- use a restrained effect on transient popovers/dialogs;
- test clipping inside scroll areas;
- do not attach an effect to thousands of item-view rows.

## QSS limitations to remember

- no CSS variables or runtime token engine;
- limited selector and pseudo-state support;
- no reliable web-style outline/box-shadow model;
- styling a complex widget can suppress parts of native rendering;
- subcontrols often need explicit geometry and state rules;
- QSS cannot implement every accessibility or interaction behavior.

When a stylesheet begins to emulate a complete control renderer, reassess whether a delegate, proxy style, or small custom widget is clearer.

## Safe application order

A typical startup sequence:

```python
app = QApplication(argv)
repository = TokenRepository.from_skill_resources(...)
manager = FluentThemeManager(app, repository)
manager.set_mode(ThemeMode.SYSTEM)
manager.apply()
window = MainWindow()
window.show()
```

For expanded-client-area title bars, set the required window flags before first show, then bind safe-area handling after a `QWindow` exists.
