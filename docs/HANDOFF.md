## 当前继续推进

近期建议分成两条互不混淆的路线。

### A. 先把现有桌面版做成稳定演示产品

1. 使用当前双摄硬件完成一项真人肩外展和一项坐站闭环：测试摄像头 → 评估 → 身体汇总 → 自动计划 → 训练 → 反馈 → 重开报告。
2. 用人工计数和量角/视频标注核对骨架、角度、分期、计次和保存；软件测试不能替代真人准确度证据。
3. 逐批核对工作区中的动作图片：动作、侧别、起点、出程、回位和使用权一致后，再运行导入脚本并单独提交。不要把当前未提交图片目录直接当作已接入素材。
4. 邀请陌生使用者完成一次流程，记录其是否能理解下一步提示、远距离大字、暂停/停止和训练后反馈；再针对实际卡点调整。

后续接入摄像头时，可按[双摄说明](history/DUAL_CAMERA_V0_13.md)先测试两路原始画面。开发工具 `check_dual_camera.py` 可记录显式选择的设备同时采集、实际帧参数及停止重开；不会推理或保存视频，不能代替真人动作对照。录像验证需保留 `REPLAY_FILE` 来源和人工对照；软件合成测试继续标记 `SYNTHETIC/TEST`。

### B. 网页化并部署到阿里云

网页化是一次架构改造，不是给现有 PySide6 程序补一个 Dockerfile。推荐的最短路径是：

1. 新建浏览器前端，使用 `getUserMedia` 显式选择正面/侧面设备，显示现有步骤、大字提示和报告。
2. 新建 FastAPI + WebSocket 服务，接收带设备角色和时间戳的压缩帧；每路只保留最新一帧，避免积压增加延迟。
3. 从现有代码中复用姿态推理、几何、动作状态机、身体汇总、自动计划和报告；移除云端镜像中的 PySide6、Windows 摄像头枚举及本地 `VideoCapture` 入口。
4. 第一阶段使用 Linux/AMD64、Python 3.11、`opencv-python-headless` 的 CPU 镜像；模型随镜像固定，不在容器启动时联网下载。单容器先设 1 个推理 worker、1 个活动双摄会话。
5. 推送到同地域 ACR，在 4 vCPU / 8 GB ECS 上以 Docker Compose 运行，Nginx 只向公网开放 80/443，应用端口仅本机可见；配置正式域名和 HTTPS 后浏览器才可稳定授权摄像头。
6. 实测端到端帧率、带宽、两路配对、断流、模型延迟与内存后，再决定是否升级 8 vCPU / 16 GB 或 GPU。SQLite 只适合单机演示；多用户生产版迁移到 RDS，并将导出文件放 OSS。

云端首个验收目标应限制为“一个浏览器、一个用户、一个双摄康复任务、保存并重开报告”。在该闭环通过前，不先宣称多用户远程康复平台已经完成。
