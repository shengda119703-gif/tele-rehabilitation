# 康复助手程序操作 V1

## 目标

让康复助手不只“回答”，还能够在用户明确要求后修改本人的康复计划或训练安排。

当前第一版只开放：

- 修改当前计划名称
- 修改当前计划已有动作的支持参数
- 添加动作（必须来自真实动作库）
- 删除当前计划动作
- 新增/修改康复训练安排时间
- 删除康复训练安排

导航类请求（如“打开康复页面”）继续走已有模块导航，不进入本写入链路。

## 调用链

```
用户语言
  ↓
LLM① Johnson
  ↓
route / intents
  ↓
发现 program_operation / plan_change
  ↓
LLM② 决定需要读取什么
  ↓
Host 只读
  ├─ 当前康复计划 + revision
  └─ 当前训练安排
  ↓
LLM③ 生成候选操作 JSON
  ↓
Host preview
  ↓
程序验证
  ↓
给用户展示“准备这样修改……”
  ↓
用户明确确认
  ↓
Host commit
  ↓
Storage / DailyStore 原子写入
  ↓
刷新 snapshot
```

## 关键原则

### 1. LLM 不直接写数据库

模型只能提出：

`rehab.plan.change`

`rehab.schedule.upsert`

`rehab.schedule.remove`

实际写入由 Python Host 执行。

### 2. 必须先预览、再确认

候选操作使用 `commit:false` 进入 preview。

只有下一轮用户明确表达确认，例如“确认”“可以”“按这个来”，程序才使用 `commit:true`。

如果用户说取消，pending proposal 丢弃。

如果用户没有确认而开始新的话题，旧 proposal 丢弃，避免稍后的“好”误执行旧操作。

### 3. 乐观并发控制

计划操作携带：

- `plan_id`
- `expected_revision`

保存时由现有 `Storage.save_training_plan()` 再次检查 revision。

训练安排还绑定 preview 时看到的原安排；如果确认前安排已经变化，commit 拒绝。

## 与康复分析联动

例如：

“我今天膝盖不舒服，先把今天的腿部训练停一下。”

第一轮 Johnson 可以同时识别：

- `rehab_question`
- `program_operation`

康复分析分支先读取个人数据、动作知识库和算法，形成分析结果。

程序操作分支再读取当前计划，形成“待确认修改”。

**注意：康复分析本身不能直接写计划。**

最终应形成：

```
康复分析结果
+
待修改计划
+
用户确认
↓
程序写入
```

如果属于既有安全处置路径，安全路径优先，程序写入不会绕过它。

## 当前尚未做

- 暂停/恢复整个计划的状态操作
- 拖拽/重排动作
- 训练完成状态自动写入
- 自动把新生成计划直接采用
- 用户确认后的 UI 局部刷新动画
- 多个写操作的事务性组合

V1 故意一次只允许一个写操作，避免“改计划 + 改时间”出现部分成功。
