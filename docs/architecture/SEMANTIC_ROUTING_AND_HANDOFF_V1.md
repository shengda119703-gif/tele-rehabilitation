# 康复助手语义分流与兜底 V1

## 设计结论

面向用户的主路径按任务分为五类：

1. 普通聊天（`chat`）
2. 一般健康咨询（`health`）
3. 康复动作、训练和恢复分析（`rehab`）
4. 应用操作（`module`、`records`，以及 `program_operation` 意图）
5. 超出范围或无法可靠处理（`other`）

`records` 和 `module` 是现有应用能力入口，不是新的医学分析分支。一个请求可以包含多个意图，例如 `rehab_question + program_operation`。

现有安全/临床规则优先级最高，在语义执行和任何程序操作之前运行。语义路由不能覆盖它。

## 处理流程

```
用户输入
  ↓
第一轮 Johnson：解析 route / intents / evidence / uncertainty
  ↓
现有安全与临床规则
  ↓
语义结果结构化校验
  ↓
┌ chat ──────────────── 普通对话
├ health ────────────── 一般健康信息与必要追问
├ rehab ─────────────── 读取允许的数据、动作知识、指导资料和算法
├ records ───────────── 本人范围内的只读记录查询
├ module / program_operation ─ 已注册的页面/计划/安排操作
└ other ─────────────── 范围策略与升级提示
```

## Other 不是“自动转医生”

兜底路径根据请求性质给出三种结果：

- `clinical_handoff`：用户要求诊断、处方、个体化治疗决定，或明确要求咨询医生。说明需要合格临床人员判断，可帮助整理就诊问题，但不会声称已经联系医生。
- `unsupported_operation`：用户要求当前没有接通的外部操作，例如预约、打电话、呼叫服务或未实现的提醒。明确说明没有执行，不生成成功回执。
- `out_of_scope`：与当前康复助手功能无关，或当前无法可靠分类。简要说明支持范围，并邀请用户换一种目标描述。

显式的诊断/治疗决策请求，即使 Johnson 将其路由到 `health` 或 `rehab`，也会进入临床边界提示。普通症状咨询不会因此自动转诊。

## 医疗安全边界

- 现有 safetyAction / 临床规则先于此模块；此模块不替代急症识别或分诊规则。
- 不把模型的回答包装成诊断、处方或个体化治疗决定。
- 不因请求超出范围就一律要求就医。
- 不自动预约、呼叫医生或救护服务；没有对应 Host 工具就明确说明未执行。
- 对紧急或快速恶化的情况，保留现有安全处理，并提示用户及时联系当地急救/医疗服务。

## 验收范围

- `other` 路由会得到明确、有限的兜底回复，不再进入没有边界的通用回答。
- 诊断/处方请求在 `other`、`health`、`rehab` 路由下都能触发临床边界提示。
- 预约或未接通的操作明确说明未执行。
- `chat`、普通健康咨询和康复分析继续由原有分支处理。
- 兜底不调用个人记录工具、不调用写操作工具、不新增健康记录。
