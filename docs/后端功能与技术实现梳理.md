## 0. 先看全局：你要优化的不是一个总准确率

这份文档的用途，是让团队能从一个错误结果追回它的输入、算法、业务引用和保存位置。建议先读本节、第2节和第3节；确定要研究的问题后，再到第24节找函数、第26节找实际参数、第19节选评价口径。其余章节保留详细实现和工程证据供追溯，不需要一次全部读完。

### 0.2 一次肩外展评估怎样影响后续训练

下面按原电脑版路径举例，使用实际对象／函数名；不是新增统一接口。录像使用媒体时间及REPLAY_FILE来源，APK和v2另有实现，不能直接套用这条路径。

| 顺序 | 输入 → 计算／判断 → 输出 | 下一跳为什么需要这些信息 |
| --- | --- | --- |
| 1：采集与推理 | `FramePacket`图像／seq／源时间 → `VisionWorker` → `PoseFrame.people[].xy/conf/track_key/bbox`及顶层骨架／尺寸／上下文 | 几何必须知道点对应谁、哪一帧、哪种骨架与坐标；处理耗时不替代动作发生时间 |
| 2：点到角度 | `PoseAnalyzer.analyze`延续人物、验证点、因果滤波 → `Observation.metrics[metric_id].value/valid/reason` | 肩外展主指标使用所测侧肩肘；独立躯干代偿缺测不能补成正常或当作主角度为零 |
| 3：角度到动作事实 | `RehabEngine`读取有效角度和计划 → 起点／离开／转折／回位 → 完整或部分次、目标状态、时间与summary | 报告与身体汇总读取已确认事实；指导只消费状态，不反向决定已经完成 |
| 4：结束并保存 | 原`Storage`保存session、逐次、summary和配置条件 → `build_body_profile`按本人／来源／情境／动作侧别取最新 | 汇总保留session ID、范围、覆盖和契约；最新不可用不能自动换成旧最好结果 |
| 5：评估到计划 | `generate_proposal`检查证据／限制／反馈 → 候选、排除原因、目标和指纹 → `create_automatic_plan`保存明确确认 | 原评估ID／指纹、rule version及计划revision说明目标从哪里来，之后可追查测量误差怎样影响安排 |
| 6：计划到训练 | 读取`assessment_reference`与`saved_plan_reference.id/revision/entry_key` → `TrainingEngine`执行冻结条目、组次和休息 | 动作名称相同不能代替计划身份；新评估不得悄悄改写正在执行的旧条目 |
| 7：训练到继续／报告 | 保存训练事实＋独立`training_feedback` → `program_progress` → done／quality／blocked／next_key；历史与管家读保存结果 | 次数完成、目标／可观察质量、自评与保存状态分别判断；没有自评不等于无痛，报告失败不等于应再记一次训练 |

因此，若肩角度被低估，可能先影响转折与次数，再影响汇总准入及生成目标；如果次数正确而历史缺失，应先查保存／引用，不应先换模型。详细字段与连接键在第3.1、3.7节，完整例子在第17节。

### 0.4 两类验收分开做

**准确性**用独立参考判断“测的对不对”：点误差、角度误差、完整／部分次、阶段时间、器械位置与导数、健康事实理解。每项同时报告有效覆盖、无法评价比例和条件分组；不只挑成功片段。

**可靠性**判断“结果能否及时、唯一、正确归属地保存与取回”：队列和证据年龄、控制延迟、超时／重试、断流／退出、事务、反馈与报告版本、权限和真实送达。已有隔离工程验收不能替代真人或目标手机验证。

第一轮最小讨论单位可以是“一个肩动作＋一个下肢／功能动作＋一条健康或照护信息链”。同一批固定输入，沿上表保存每一跳的结果，找到最早偏离独立参考的位置；一次只比较一层修改。第19节给评价公式，第24.3节给实验记录模板，第25节给停止条件。这是建议的研究顺序，不表示本次已实施任何优化。

| 已看到的事实 | 它能说明什么／不能说明什么 | 建议先做的只读定位实验 |
| --- | --- | --- |
| 24段真实RGB的TCN／Ridge没有优于分数中位数常量 | 输入到视频分数的训练链可运行，但本批不支持模型有泛化优势；视频评分不是逐帧点／相位标签 | 保留固定test，用新的训练内验证检查样本量、特征覆盖、评分分布和模型容量；需要动作层优化时另建独立相位／点参考 |

## 1. 全局结构：后端不是一个“大模型”

项目由三条主要业务链和若干公共能力组成。

```text
动作链
相机／录像 → 身体或手部关键点 → 几何指标 → 动作相位／计次／质量
 → 评估记录 → 康复身体汇总 → 建议与计划 → 训练执行 → 感受与进度

健康链
手动／对话／设备适配／图片确认 → 健康事件 → 每日指标
 → 个人基线／变化发现 → 管家解释、照护任务、获准家庭摘要

照护链
既有药物／训练安排 + 明确意图 → 待确认工作流
 → 人工确认 → 原事实复核 → 幂等业务提交 → 回执

公共能力
档案与权限／时间和身份／队列与所属进程／持久化／报告与导出／离线验证
```

这里的康复身体汇总与健康 `PersonTwin` 不同：前者汇总动作和侧别的评估；后者汇总日常健康指标、主诉与变化。现有代码没有把二者合并为可用于疾病诊断的人体模型。

### 1.1 三种运行方式

| --- | --- | --- | --- | --- |

### 1.2 一次请求在哪个后端运行

| 请求／输入 | 入口 → 实际计算 | 结果保存与返回 | 与其他链路的连接 |
| --- | --- | --- | --- |
| 电脑相机评估／训练 | `Runtime`／`SceneController` → 采集进程 → `VisionWorker` → `PoseAnalyzer` → `RehabEngine`／`TrainingEngine` | 原 `Storage` 保存会话／逐次／快照；呈现端读取当前状态及保存结果 | 原身体汇总、自动计划、训练进度和康复只读工具读取这些事实 |
| 电脑健康记录／管家对话 | `ProductBackend` 单 worker → `AgentBridge` 的 Node JSON 行请求 → `ProductService`／理解／事件／检测 | 产品 JSON 保存健康事实及派生状态；回复通过所属请求队列返回 | 组合快照另外读取康复 SQL、日常 SQL；不是把三种存储合成一张表 |
| 统一手机网页的查询／安排 | `PhoneHost`／FastAPI → `SharedProduct` 固定 owner → 同一电脑 `ProductBackend` | 当前本人快照或原业务写入回执 | 白名单与并发槽在网页宿主检查；不允许请求自己指定另一个本人 |
| 手机上传录像 | `POST /api/jobs` → 保存原片／job → 所属 `mobile_rehab.analyzer` 子进程 → 康复／健身／体态分析器 | job 的 result／error 与媒体文件；康复路径另存会话引用 | 对接历史、评估身体汇总、原录像计划；与实时来源保持区别 |
| 原实时预览 | `/api/live` → 有限帧推理／本次预览状态 | 返回预览指标；停止预览不产生正式训练 commit | 不能把预览成功等同于训练历史保存 |
| 独立 APK 录像／实时入口 | 复用页面 → `local-api.js` 路由适配 → `PhoneMotion`／MediaPipe Worker → `LocalEngine` | 本地业务状态与媒体存储；`store.serial` 串行组织业务操作 | 复用 ProductService 领域规则，但视觉、计划和继续算法另有手机实现 |
| 康复 v2，默认关闭 | 认证 API → `SessionService` → 所属推理进程 → `EvidenceAdapter`／协议／组次 | 独立 v2 SQL 中的最终事实／贡献／反馈；报告另有所属进程 | 当前没有自动替换以上旧路径；前端、APK 和旧只读工具还需适配 |
| 研究／误差评估 | CLI → 受权限／身份／划分约束的数据工具 → 基线／TCN 或 RGB 姿态训练器 | 忽略目录中的逐样本预测、检查点和模型卡 | 产物不是患者历史，候选不会因训练成功而自动接产品 |

这里要区分三个词：**计算结果**可能只在内存或 job 文件中；**保存事实**需要所属存储确认；**组合快照**是查询时聚合的视图。一个请求返回成功，不保证全部相关存储、派生报告和外部渠道都已完成。

源码定位：[ProductBackend](../rehab_codex_single_camera_v2_1/app/product/backend.py)、[AgentBridge](../bridges/ankang/client.py)、[PhoneHost](../mobile_rehab/desktop.py)、[APK 动作入口](../android_offline/web/motion.js)、[APK 业务串行器](../android_offline/web/store.js)。不要把手机网页理解成手机内的 Python 服务。

### 1.3 算法、业务事实和展示结果的分界

```text
                     ┌─ 电脑／托管网页：Python 视觉与动作引擎
相机／录像 ───────────┤
                     └─ 独立 APK：MediaPipe Worker + JS 动作引擎
                                  │
                                  ▼
                         指标、相位、逐次结果
                                  │
                                  ▼
                        所属康复存储／本地作业
                                  │
                                  ├─ 身体汇总 → 建议 → 冻结计划 → 训练与自评
                                  └─ 历史／报告／管家只读查询

文字／设备读数／图片确认 → ProductService → HealthEvent → 日数据
                                                  ├─ 基线 → Finding／PersonTwin
                                                  └─ 授权投影 → 家庭摘要／通知

已有服药／训练安排 + 确认 → 原业务事务 + Receipt → 今日安排／管家查询

默认关闭 v2：独立事实库 → 唯一贡献／追加自评 → 可重建报告
研究工具：独立参考 → 离线评价／候选模型；不写上述患者事实
```

这张图按职责归类，不是统一进程图。第一行的两套视觉实现没有共享一份状态机；图中的“所属存储”也不是同一数据库。原康复记录、健康事件、照护回执和v2事实通过明确读取或转换连接，不能仅凭名字相似互相替代。

优化时把结果分成四层检查：**原输入是否对应正确的人和时间，算法是否正确测出定义的量，业务是否引用了正确版本，存储是否确认了这次事实。** 报告、文字和曲线放在最后核对；它们无法弥补前面某一层出错。

三条信息链应分开验收：

1. **事实查询**：原话→意图／工具计划→整个计划校验→本人真实读取→逐步结果→解释。康复事实只读进入管家，不重新测量，不把安排当完成。
2. **普通对话**：原话→健康／安全／操作路由→获准普通聊天历史→模型请求→完整响应检查→带来源回复。同步消息不能认证为本机曾经发给模型；对话成功不代表工具或健康写入成功。
3. **照护写入**：原话→原记录／计划→待确认→明确确认→expected再核对→宿主原子保存＋幂等回执→安排或再次查询。模型帮助理解，业务成功必须有宿主证据。

### 2.2 从后端算法入手的起步实验

以下是**候选实验，不是本次已经安装或接入的算法**。先固定原输入与独立参考，每次只改一层，再沿2.1节链路核对下游。没有独立参考，可以证明差异或恢复行为，不能证明真人测量更准确。

| 优先定位的问题 | 当前实现／入口 | 可比较的候选方法 | 不能省略的验收 |
| --- | --- | --- | --- |
| 点抖动、峰值偏小、转折提示迟到 | F07因果EMA；PoseAnalyzer.analyze | 原EMA的τ对照；再试速度自适应One Euro滤波。其截止频率随速度调整，适合研究抖动与响应延迟的权衡；这是候选选择，不是已证明适合本项目的结论 | 原点与骨架固定；分别测静态抖动、角度偏差、峰值衰减、转折延迟、覆盖与计次；无效点及缺口处理不能放宽。[算法作者资料](https://gery.casiez.net/1euro/) |
| 杠铃速度／加速度跳变 | F19模板匹配＋实际时间局部二次拟合 | 先改跟踪或标尺中已定位的错误；在同一可靠轨迹上比较原拟合与Savitzky–Golay导数。后者有导数阶数和采样间隔参数，不应把不规则时间直接当等间隔样本 | 独立位置参考、真实时间、标尺平面、丢跟、拟合残差、v／a／功率误差；居中窗口只作离线结果，实时算法须明确因果性和延迟。[SciPy接口说明](https://docs.scipy.org/doc/scipy/reference/generated/scipy.signal.savgol_filter.html) |
| 手机与电脑结果不同，降帧后漏次 | F06不同模型；APK worker／本地规则与电脑引擎独立 | 同原片、同源时间、同解码坐标，分别导出各端点与规则输出；先隔离模型差异，再比较时序规则。MediaPipe VIDEO按帧时间处理且同步推理会阻塞所在调用线程，Worker与时间定义需要一起检查 | 不把原始像素、归一化点和world点混算；采样／队列丢帧显式记录；目标手机持续性能与计次共同验收。项目已有Worker，但不因此证明全天稳定。[Google官方说明](https://developers.google.com/edge/mediapipe/solutions/vision/pose_landmarker/web_js) |
| 提醒不合实际，管家记错人／日期 | F25事件归一、F26基线、F27语义理解 | 先建立原句→人物／日期／否定／实际事件的标注对照；输入正确后再比较现有均值／标准差与稳健基线，而非先换更大语言模型 | 原事实、单位、测次、样本覆盖、误报负担与私密字段投影；规则分数仍不当疾病概率；详见22.5节 |
| 做完但未保存，重试重复或报告不一致 | 原ProductBackend／jobs；F33会话与存储边界 | 在隔离库中比较超时、重复请求、旧epoch、报告失败与恢复。先补幂等／版本／跨存储对账；算法输出保持不变 | 权威事实数、唯一贡献、原幂等键、反馈revision、报告版本及真实退出；可靠性不能用角度MAE代替；详见15.4、22.7节 |

模型分数高、自动生成计划成功、报告看起来合理，分别不能代替点级误差、计划依据正确、事实已保存。建议第一轮只选择一个肩动作和一个下肢／功能动作，收集独立参考后跑完整链路；第19节给评价口径，第24、26节定位函数／参数，第25节给改进任务和停止条件。

### 3.1 逐跳信息交接：从字段定位算法

| 上游真实对象／字段 | 怎样产生 | 下游消费 | 必须保持的含义 |
| --- | --- | --- | --- |
| `PoseFrame.people[].xy/conf/track_key/bbox`；顶层 `context/seq/time_s/size/schema_id` | 图像推理、跟踪与帧封装 | `PoseAnalyzer`、几何和各场景引擎 | 不同人物、骨架顺序、原像素尺度和源时间不能混用 |
| `Observation.metrics[metric_id].value/valid/reason` | 必要点校验、因果去噪、几何计算 | 相位、计次、质量和指导 | 辅助指标无效不等于主指标数值为 0；原 `Metric` 不包含 v2 的全部年龄字段 |
| 原 `session.summary.motion_range.{min_deg,max_deg,range_deg}`、`valid_ratio/completed` | 本次结束前的幅度证据、覆盖与确认次数 | `build_body_profile` | 范围是本次观察，不是治疗目标；有效比例不是准确率 |
| 身体汇总 `items[].session_id/status/conditions/motion_range/completed` | 同本人、来源、情境、动作及侧别取最新结束评估 | `generate_proposal`、训练参考 | `ASSESSED` 不自动意味着符合建议准入；最新失败也要保留 |
| 建议 `candidates[].assessment_id/assessment_fingerprint/settings`；顶层 `fingerprint/participant_fingerprint/blockers` | 评估、档案、适用条件和版本化规则 | `create_automatic_plan` | 数值、原证据、参与者和规则版本是一组，不能只传最终角度 |
| 原计划 `id/revision/items[].key/settings`；`automatic.entries/body/screening` | 保存条目、冻结评估依据和确认 | 准备训练、`validate_automatic_use` | 自动依据在 `automatic` 内；计划修改会影响 revision 和继续资格 |
| 执行 `assessment_reference`、`saved_plan_reference.id/revision/entry_key/item/session_overrides` | 读取并核对原计划与条目 | `TrainingEngine` → 训练存储 | 动作名称不能替代保存的计划绑定；本次覆盖参数需另存 |
| 训练 `summary.plan_completed/repetitions/training_feedback` | 组次状态、逐次证据、独立自评 | `program_progress().items[].done/quality`、`blocked/next_key` | 完成、质量、疼痛与疲劳不同；空自评不是无不适 |
| 健身 `result.summary/repetitions/series`；可选 `barbell.calibration/lifts/series/summary` | 身体几何规则；另行标定的器械跟踪和求导 | 健身历史、曲线、器械表现 | 人体动作次数和器械上升段不是同一事件；器械结果有独立覆盖要求 |
| `HealthEvent.measurement.metric/value/unit/visibility/metadata` 或 `observation.text/tags/status/visibility` | 数值归一或接受的主诉 | 日数据 → 基线／变化发现 → 管家 | 权限和否定／假设状态在具体内容内，不能展平后丢失 |
| `Finding.ruleId/severity/evidence/score/signalKeys/familyEligible` | 健康规则与多信号融合 | 管家优先级、任务和通知 | evidence 当前不保证全部是稳定原事件 ID；仍欠全量逐证据血缘 |
| `CareWorkflow.id/requestId/scope/steps[].action.expected/expiresAt` | 原业务事实和明确意图形成提议 | 明确确认 → 原事实复核 → 宿主执行 | 凭证不能记录进普通日志；expected 防止提议后原事实改变仍被覆盖 |
| `CareReceipt.status/idempotencyKey/operation`；工作流 `steps[].receipt` | 宿主执行与事务回执 | 重试、恢复、今天安排和管家查询 | 提议存在不是已执行；重试先查原回执 |
| v2 `snapshot.completed/repetitions/training`；`canonical_commit.visual_snapshot_digest` | v2 协议、组次与最终事务 | v2 历史、唯一贡献、派生报告 | 封套不等同原 `summary`；不能直接写进旧评估汇总 |
| v2 `feedback_revision/feedback_status/latest_feedback/derived_report_state` | 最终事实后追加自评及独立报告 | 继续政策、报告查询／重建 | 新反馈可增版本，原视觉事实不回写；旧报告不能覆盖新反馈 |

### 3.2 常见百分比和完成状态不是同一口径

| 当前路径 | 数值或状态的实际含义 | 误用会造成什么 |
| --- | --- | --- |
| 电脑评估 `summary.valid_ratio` | 有效观察时间／首末观察跨度；无跨度为 null | 当成正确率，或和有效帧比例直接比较 |
| 电脑训练 `summary.valid_ratio` | 有效时间／活动跨度，上限 1；休息与暂停另计 | 以整个会话时长作分母会错判覆盖 |
| 电脑健身指标 `coverage` | 指标可测样本数／处理帧数 | 不规则采样时不能替代按时间统计 |
| 电脑体态 `coverage/sample_count/variation` | coverage 看全部处理帧；值、样本数和 MAD 看所选连续片段 | 高总体覆盖可能没有足够连续稳定片段 |
| 器械 `tracked_ratio` | 有 y 轨迹样本／全部输入样本 | 轨迹存在不证明加速度和功率可靠 |
| APK `LocalEngine.report().validRatio` | 有效时间／首末跨度，无跨度返回 0 | 与电脑 null 不同；合并统计会掩盖无法评价 |
| 电脑 `summary.plan_completed` | 完成组数达到目标组数 | 被误读成每次幅度、节奏、代偿都合格 |
| APK 适配的 `summary.plan_completed` | 有目标时符合其目标判定的次数达到次数×组数 | 与电脑版同名字段不保证同算法 |
| v2 `snapshot.training.plan_complete` | 显式目标组数全部确认 | 原字段不能未经契约检查直接复制 |
| v2 `commit` 回执 | 本次会话权威最终提交 | 不证明报告已生成、家属已收到、整个治疗计划已结束 |

后续统计同时报告：数值误差、有效覆盖、完成判定、继续资格和保存状态。不要用一个百分比替代这五项。

### 3.3 哪些功能已经相接，哪些还没有自动闭环

| 上游 → 下游 | 当前真实连接 | 后端优化时要保持／补齐什么 |
| --- | --- | --- |
| 原康复评估 → 身体汇总 → 自动建议 | 已接；依据同作用域的最新结束评估，保留评估 ID／契约与指纹 | 主指标误差、覆盖或完成状态改变，会改变候选准入及训练目标 |
| 保存计划 → 训练 → 自评 → 下一项 | 已接；原计划身份与版本绑定，自评影响继续资格 | 次数完成、目标达标、可观察质量和用户感受不能压成一个布尔值 |
| 原康复历史 → 管家 | 通过限定作用域的只读工具／组合快照相接 | 查询不补造新测量；新指标需同时定义只读投影与解释口径 |
| 康复身体汇总 → 健康 `PersonTwin` | 没有自动合并为同一个身体模型 | 两者对象、时间窗和含义不同；如需融合，要定义事件映射和证据血缘 |
| 健康 `Finding` → 自动康复计划 | 目前不是“检测到变化就自动改计划” | 原计划规则检查档案限制／原筛查／训练反馈，不直接消费所有健康风险分数 |
| 管家提议 → 用药记录／训练改期 | 有 prepare／confirm／宿主事务回执；正式确认卡片尚未接通 | 人物、时段、原事实和明确确认先正确；不自动改变医嘱或启动训练 |
| 健身人体动作 → 器械动力学 | 同一报告可并列两组结果；计次与器械上升段仍独立 | 器械缺测不能伪装人体动作失败，人体计次成功也不证明功率可用 |
| 产品快照 → 家庭 | 按关系、类别与可共享事实投影，渠道有各自状态 | 摘要生成不等于家属送达；私密事实不能因聚合视图而泄露 |
| APK → 辅助云端 → 电脑库 | 文字备份／获准摘要可以传；不是全量自动合库 | 归属、revision、冲突与来源先定义，再扩展媒体或业务同步 |
| v2 → 原历史／原计划进度／APK | 新库与唯一贡献已有实现，但尚未默认接旧消费者 | 需要显式契约适配；不能把 v2 snapshot 直接当原 summary |
| 离线训练 → 正式模型 → 下游动作链 | 研究产物与门控存在；没有自动上线 | 同域独立证据、骨架／坐标、性能、版本迁移和回退需单独验收 |

因此，“功能在同一程序里”不等于“功能已经自动交换所有信息”。优化讨论应指定要改哪一条现有连接，或者要新增哪一份明确的转换契约。

### 3.4 一份结果传下去时，哪些信息不能丢

以下是对现有字段的交接要求，不是已经实现的新统一封套。不同路径没有的字段需标为未知，不能假称全部后端已经记录完整血缘。

| 信息类别 | 当前可以从哪里读取 | 下游需要它做什么 | 典型丢失错误 |
| --- | --- | --- | --- |
| 归属 | 原会话 `participant_id`、产品 owner、v2 owner；来源／情境作用域 | 决定该记录属于谁、哪些记录能组成计划或分享 | 把当前 track 当本人，或按动作名称合并不同人 |
| 输入身份 | `Context.source_ref/run_id/epoch`、帧 `seq`；研究工具另有文件／像素hash | 对应原帧、拒收旧上下文、复现实验 | 用邻近帧标签评价当前帧；以为所有正式帧已有hash账本 |
| 测量定义 | 骨架、点顺序、原像素坐标、模型／预处理／规则／measurement contract | 判断指标含义、历史可比性和版本迁移 | 手机和电脑字段同名就直接比较；镜像后重命名解剖学侧别 |
| 时间 | `time_s/time_basis/received_monotonic`；健康 `timestamp`；v2证据年龄 | 计算阶段、保持、新鲜度和当地日期 | 用推理耗时当运动时间，或相减两台设备的单调时钟 |
| 可测性 | 原 `Metric.value/valid/reason`；逐次目标／质量状态 | 决定能否参与范围、计次、质量和计划 | null被补0，辅助指标缺测导致主指标整体失效 |
| 依据和版本 | 评估ID／指纹、plan ID／revision／entry_key、规则版本 | 使用和继续前核对原依据，避免旧计划串到新记录 | 只传最终角度／次数，丢掉评估依据和条目身份 |
| 保存和投影状态 | session保存结果、v2 canonical commit、Care receipt；派生报告／渠道状态 | 区分已提交、可重建、待送达和失败 | 将HTTP成功、报告ready或本地显示当全部业务完成 |
| 权限和来源 | source kind／usage context、健康内容内visibility、家庭类别授权 | 区分测量、自述、手工、研究以及谁可以读取 | 摘要聚合时丢私密标记；把自述当摄像头测量 |

必须保留三种不同含义：**测得0、没测到、这次处理失败**。例如完成0次可以是真实观察结果；角度null表示无可用值；任务failed表示作业未按预期结束。它们不能在序列化、报表或统计时变成同一个0。

目前最值得补齐的交接是：原业务与v2的显式适配、健康Finding到稳定原事件ID的血缘、跨端测量契约，以及跨文件／数据库的对账。它们解决的是“这条结果能否被正确使用”，不应混在模型准确率里评价。

### 3.5 读写依赖：算法结果怎样进入后续功能

下表说明实际读取关系，不是一份已经统一实现的消息总线。仅计算出数值、保存原事实、生成组合视图和向外投递，是四件不同的事。

| 上游结果 | 写入／保留位置 | 当前下游读取者 | 修改算法后必须跟着核对 |
| --- | --- | --- | --- |
| 原康复会话与逐次结果 | `Storage`中的会话、快照与repetitions | `build_body_profile`、历史／纵向比较、原康复只读工具 | participant、来源情境、动作侧别、测量契约、结束状态；不能只传一个最大角度 |
| 动作＋侧别的最新评估 | `build_body_profile`查询时构建，不自动成为健康事件 | `generate_proposal`、`build_training_reference` | 失败／未测状态、范围和覆盖分母；最新失败不回退旧成功 |
| 原自动提议 | 内存／接口中的候选、指纹与排除原因 | `create_automatic_plan` | 原评估、档案、筛查和规则指纹；提议本身不是已保存计划 |
| 已保存原计划 | 原康复库的plan／revision／items | `validate_automatic_use`、训练冻结引用、`program_progress` | 使用时重新核对依据；条目和版本不能被新算法静默改写 |
| 已保存训练＋自评 | 原会话与反馈字段 | 原计划进度、下一项资格、管家只读历史 | 完成组次、幅度／节奏／质量与疼痛／疲劳分别保留 |
| 健身人体与器械结果 | 托管job的`result.json`；APK有独立本地结果 | 对应作业查询、健身历史／报告 | `summary/repetitions/series/barbell/conditions`；不自动写入康复评估或病种计划 |
| 体态稳定片段结果 | 体态job的`summary.metrics`与条件 | 对应体态历史／报告 | value、valid、样本数、覆盖、variation、机位；没有自动并入PersonTwin |
| 接受的健康事实 | 产品健康事件存储；内容含measurement／observation／labResult | `materializeHealthData`、`deriveHealthState` | 原事件ID、人物、单位、日期、来源、事实状态与嵌套权限 |
| 日数据／主诉 | 由健康事件投影而成 | `runDetection`、`buildAgentContext`／PersonTwin | 不把同日最新值改成平均值而仍沿用旧基线；保留测次和覆盖 |
| Finding／个人健康摘要 | 派生健康状态或产品快照 | 管家上下文、照护任务、类别授权投影与通知 | evidence、ruleId、severity、score的实际含义；不能变成疾病概率或自动处方 |
| 用药或安排变化＋Care回执 | `product_daily.sqlite3`对应业务事务 | Care步骤状态、今日安排、再次查询／重试 | expected原事实、操作键、receipt及部分成功；意图理解与事务正确性分别验收 |
| 获准家庭摘要／通知账本 | 家庭关系、授权投影和通知存储 | 家庭查询与已配置渠道 | 撤权、私密字段、摘要版本、真实送达状态；本地显示不等于外部收到 |
| v2最终视觉事实与唯一贡献 | 默认关闭的独立v2 SQL命名空间 | v2历史／进度、独立自评与派生报告 | commit／视觉摘要hash、计划版本、反馈revision；旧消费者尚未默认读取 |
| 离线预测／模型／模型卡 | 忽略目录中的所属run | 独立评价、模型比较与准入门控 | 数据／参考／源码／权重hash和测试划分；不写患者历史，不自动替换模型 |

例如，改变肩外展起点算法，至少会影响“角度范围→评估是否可用→建议目标→训练目标达标→历史可比性”。改变事件日期解析，则会影响“日值→基线窗口→Finding→管家和家庭摘要”。**要验收的是整条受影响的读取链，而不只是改动函数的返回值。**

### 3.6 功能依赖速查：优化时要留住哪些中间结果

先确定要优化的用户功能，再沿这一行查最早出现偏差的计算。表中的箭头表示现有读取或调用关系，不表示已经有统一消息总线；“未接”与“条件实现”不可省略。

| 用户功能 | 前置输入与计算 | 应留存或对照的中间结果 | 接到哪个下游 | 优化验收的重点 |
| --- | --- | --- | --- | --- |
| 康复关节评估 | 所选动作／侧／view＋帧→人物点→必要点检查／滤波→几何→相位 | 原点、滤波点、基线、`value/valid/reason`、范围、完整／部分、源时间 | 原session→身体汇总→建议或训练参考 | 同一角度定义下的误差与覆盖；峰值和完整次数是否一起变化 |
| 自动基础活动计划 | 最新同范围评估＋档案限制／筛查→`generate_proposal` | assessment ID／指纹、候选／排除原因、目标与剂量、规则版本 | 保存plan／revision→使用前复核→训练 | 区分“评估测准”与“规则适用”；新失败不回退旧成功 |
| 训练与下一步指导 | 冻结条目＋连续指标→动作相位／节奏→组次→`GuidancePolicy` | 每次完成、目标、质量、cue时刻、暂停／休息、自评 | 已保存训练→原计划进度／下一项→历史／管家 | 提示是否基于已确认动作；完成和质量、自评不混成一个状态 |
| 健身动作报告 | 所选八类动作之一＋解码点／时间→几何与固定相位规则 | 范围、完整／部分、阶段边界、关键帧、有效覆盖 | 作业result→健身历史；不自动进入康复计划 | 所选动作的阶段参考；人体次数与器械上升段分开 |
| 杠铃速度／外力／功率 | 原帧＋标尺／参考点／质量→模板跟踪→米制位移→局部拟合求导 | 像素轨迹、标定比例、真实采样间隔、拟合残差、v／a／F／P及空值原因 | 健身result的`barbell`→曲线与逐段表现 | 先位置再导数；不能用20kg输入替代空间标定或有效采样 |
| 正侧面体态 | view＋连续人物点→参考线角度／偏移→有效稳定片段 | 片段边界、样本数、时长、coverage、中位数、MAD | 体态job与历史；未自动并入健康PersonTwin | 符号／参考轴、稳定段与覆盖；没有骨性标志的指标不补造 |
| 日常／卧室／疑似安全事件 | 当前观测＋ROI＋连续时间→各场景状态机 | 有效观察区间、坐站／离床链、事件状态、缺测与响应 | 对应场景存储／任务／报告；非完整疾病或救援闭环 | 误报／漏报、无人／遮挡、断流与延迟；三类场景分别测 |
| 健康变化与管家 | 原读数或接受原话→人物／日期／单位／事实状态→事件→日值→基线／规则 | 实际HealthEvent、测次、日值、基线样本、Finding evidence／score | PersonTwin／管家上下文→任务或获准家庭摘要 | 先事实再统计；规则分数不是疾病概率，康复汇总未自动合并 |
| 语音／图片录入 | 音频→转写；图片→OCR或结构化候选 | 文字草稿、候选数值／单位、确认或澄清、真实接受事件 | 对应chat／健康事件／资料；各入口写入行为不同 | 转写正确、语义正确和保存成功分别验收 |
| 用药记录／训练改期 | 明确意图＋原medId／plan及安排→提议→确认→expected复核 | 原句语义、工作流scope／期限、幂等键、逐步receipt | 原业务事务→今日安排／再次查询 | 错人、时间歧义、用量偏离先处理；事务正确不等于意图正确 |
| 家庭摘要／通知／同步 | 关系＋分类授权→事实投影→账本／渠道；云端另有revision／digest | 共享类别、私密字段排除、摘要版本、实际渠道回执／冲突 | 获准家庭查询／通知或文字备份 | 撤权后不泄露；本地显示、accepted与delivered分开，非全量合库 |
| v2权威提交与显式计划 | 认证JPEG＋冻结协议／计划→证据→组次→最终事务；显式计划另核对本人最新已提交评估 | epoch、commit、视觉hash、不可变计划revision、唯一贡献、反馈revision | v2进度／派生报告；未接正式五页／APK／旧管家工具 | 幂等／回滚／重开；报告失败不重做事实，源码发布不等于客户端接通 |
| 离线模型改进 | 合法独立参考＋分人划分→基线／训练→val选模→独立test | 数据／参考／源码／权重hash、逐样本误差与覆盖、模型卡 | 研究比较与准入；不会直接写患者历史或替换模型 | 点级改进后仍联测角度、相位、计划、性能与回退 |

公共前提是归属、时间、坐标、单位、权限和版本。相机复用、上传、队列、存储、导出、备份与身份处理分别见第4、14–15、21节；这些模块不一定计算医学指标，却决定后续算法是否拿到正确输入、结果能否保存和被正确读取。

实际讨论可以用一句话限定范围：“优化肩外展的滤波，只改变`PoseAnalyzer`滤波参数；固定点序列与几何，比较角度峰值／计次／cue，再核对建议目标和保存事实。”这样就能把算法变化和下游影响对应起来，而不会把整个后端一次重写。

### 3.7 用连接键把同一次输入、判断、保存与消费串起来

功能之间不是只传一个角度或一段回复。后端排错时，应沿下面的连接键查原对象，确认没有串人、串来源、串计划或串版本。各行属于各自现有路径，**不能把它们拼成一份已有的通用JSON**。

## 4. 输入、双摄与关键点

### 4.1 输入时间和生命周期

电脑相机由所属采集进程打开，实时路径优先保留最新帧；录像路径按媒体时间逐帧确认。分析慢不应该使录像动作变慢。Context、seq 和源时间用于拒绝旧结果、乱序和重复。

手机 MP4 的首部负时间兼容只允许跳过有限首部帧，并记录原因；中途非单调时间不能通过随意补时间“修好”。网络相机路径目前主要是有限 RTSP 短录制，再交给录像分析，不是持续监控平台。

双摄每路独立取流和推理，按接收时间近邻配对；默认允许差约 0.12 秒。主视图驱动动作，辅视图补充质量指标。尚无曝光硬同步、内外参标定、三角化或跨镜头实名匹配。两路二维点不能直接拼成三维关节角。

代码：[输入进程](../rehab_codex_single_camera_v2_1/app/source_worker.py)、[双摄配对](../rehab_codex_single_camera_v2_1/app/dual_camera.py)、[双视图测量](../rehab_codex_single_camera_v2_1/app/dual_view.py)、[网络输入](../mobile_rehab/network.py)。

### 4.2 模型与滤波

电脑主模型是 YOLO11n-pose／COCO17，结合 ByteTrack；扩展后端为 MediaPipe Pose33／Hand21。APK 使用 MediaPipe VIDEO 模式和手机独立规则，没有复制电脑 ByteTrack。

电脑 PoseAnalyzer 优先延续原 track，否则近邻匹配，首次通常选较大人体框。换焦点须重置基线。点检查包括骨架、有限值、画内位置、置信度、跳变和几何长度。

当前坐标因果 EMA：

```text
α = 1 - exp(-Δt / τ)，默认 τ = 0.12 秒
p_filtered(t) = α·p_observed(t) + (1-α)·p_filtered(t-1)
```

无效当前观测不能用旧滤波值伪装成有效新点；长间隔、换人会重置。滤波可以降低抖动，也会推迟峰值和转折。模型 confidence 不是已经校准的关节误差概率。

代码：[vision.py](../rehab_codex_single_camera_v2_1/app/vision.py)、[landmark_backend.py](../rehab_codex_single_camera_v2_1/app/landmark_backend.py)、[quality.py](../rehab_codex_single_camera_v2_1/app/quality.py)、[APK worker](../android_offline/web/worker.js)。

## 5. 康复测量：53 项动作怎样得到数值

目录包含 25 项非手指动作和 28 项手指屈伸；左右记录槽位不是额外动作类别。

| 部位 | 当前动作 | 主要测量方法 |
| --- | --- | --- |
| 肩，4 项 | 外展、前屈、后伸、内收回落 | 上臂相对画面参考轴、方向和舒适起点 |
| 肘，2 项 | 屈曲、伸展 | 肩—肘—腕三点，屈曲用 180°减内角 |
| 膝／功能，3 项 | 膝屈曲、伸展、坐站 | 髋—膝—踝；坐站另有专用相位 |
| 髋，4 项 | 外展、内收、前屈、后伸 | 骨盆参考轴或同侧肩—髋—膝投影 |
| 腕，4 项 | 屈伸、桡偏、尺偏 | 前臂和手参考线，需身体与手部空间匹配 |
| 踝，2 项 | 背屈、跖屈 | 膝、足跟、足尖参考，需 Pose33 |
| 头颈，3 项 | 侧屈、前屈、后伸 | 眼肩连线；侧位耳眼线相对水平并扣起点 |
| 躯干，3 项 | 侧屈、前屈、后伸 | 肩髋中线／骨盆轴／画面竖直及起点 |
| 手指，28 项 | 拇指 MCP／IP，其余四指 MCP／PIP／DIP 各屈伸 | Hand21 对应三点角，部分近端参考近似 |

基本公式：

```text
u = A-B，v = C-B
θ_internal = acos(clamp((u·v)/(|u||v|), -1, 1)) × 180/π
θ_flexion = 180° - θ_internal
θ_signed = atan2(u_x·v_y-u_y·v_x, u·v) × 180/π
θ_excursion = direction × wrap(θ_raw - θ_baseline)
```

这是二维投影。肩抬举没有扣除肩胛运动；头颈不是单节颈椎角；躯干不是逐节腰椎活动度。肩内收回落不是水平内收。ASIS／PSIS、C7 等点缺失，所以目前不能直接输出标准骨盆前倾角或标准颅椎角。

肩外展主角度只需所测侧肩、肘；髋可能用于独立躯干代偿指标，不应把该指标缺测解释为肩主测量失效。头前屈主测量也不统一要求髋点。

优化要先明确指标的参考轴、机位、方向、起点和名称，再讨论模型精度。不同公式测的不是同一个量时，不能用一个 MAE 比较。

代码：[动作目录与契约](../rehab_codex_single_camera_v2_1/app/exercises.py)、[geometry.py](../rehab_codex_single_camera_v2_1/app/geometry.py)、[axial_geometry.py](../rehab_codex_single_camera_v2_1/app/axial_geometry.py)。

## 6. 相位、计次、质量、节奏与指导

普通动作以“有效准备 → 离开起点 → 转折／保持 → 返回”构成完整一次，使用角度滞回和持续驻留，避免阈值附近抖动反复计数。半次、换人、转折藏在缺口里，都不能自动补一次。

坐站与普通往返不同：观察到从坐姿站起记一次，坐回才能重新允许下一次。原引擎没有显式校准时可能用首个有效姿势建立参考；首帧站姿因此是重点误差来源。v2 采用连续准备与明确姿势约束，见第 16 节。

每次应分别看：

- 完成状态：完整、部分或无法评价。
- 目标状态：是否设置、是否达到幅度／时间目标。
- 质量状态：已配置且可观察的代偿条件是否超限。
- 计划状态：明确组数、次数是否完成。

肩动作已有肘屈曲、躯干倾斜等限值规则；未配置或看不到，不代表“没有代偿”。目前没有经过目标人群验证的全身动作质量模型。

节奏记录出程、端点驻留、回程。结束后分段可使用峰区和中位数；实时保持只累计当前连续有效达标区间。十个间隔为 0.05 秒的样本覆盖 0.45 秒，不是 0.50 秒；缺测、暂停和换人不能跨区间续保持。

GuidancePolicy 读取已确认相位产生下一步指令，并应用优先级、冷却与取消。文字、图片或语音只消费指导，不反向制造动作完成事实。引导计时、人工记次与自动测量需保留各自来源。

代码：[RehabEngine](../rehab_codex_single_camera_v2_1/app/rehab.py)、[movement_timing.py](../rehab_codex_single_camera_v2_1/app/movement_timing.py)、[guidance.py](../rehab_codex_single_camera_v2_1/app/guidance.py)、[guided.py](../rehab_codex_single_camera_v2_1/app/guided.py)。

## 7. 评估如何变成训练计划

### 7.1 评估身体汇总

按本人、来源、情境筛选结束评估，再对动作＋侧别取最新记录。输出 `ASSESSED／UNAVAILABLE／NOT_ASSESSED`、session ID、范围、完整次数、有效观察比例、条件和问题。最新失败不悄悄回退过去最好成绩。

批量评估维护顺序、revision、跳过与完成；汇总不自动补全未测动作，也不从角度推断疼痛、病种或禁忌。

### 7.2 自动建议的真实逻辑

当前是 `general-activity-rules-1` 规则，不是神经网络处方。部分动作有具体公开基础活动材料映射，其余按一般活动原则适配，不能称全部动作都有病种专属指南。

电脑版主要检查：最新证据不超过 7 天、不在未来、结束状态及测量契约有效；有效观察比例至少 0.8、至少一个完整动作；本人限制、筛查、近期不适和疲劳按原规则处理。

```text
已观察范围 [low, high]
增大型：target = low + 0.8×(high-low)
减小型：target = high - 0.8×(high-low)
```

这些是当前工程规则，不是推荐患者照此训练的医疗建议。肩前屈／外展还有目标上限；范围不足、不在可用域或坐站时不给该角度目标。默认最多 4 条；每项一组，次数不超过当前观察到的完整次数且最多 5 次，休息 60 秒。

计划保存原评估 ID／指纹、participant／proposal 指纹、rule version、筛查、目标与剂量、条目身份。使用前重新校验当前版本和依据。保存计划 ≠ 已开始训练；旧计划不被新评估悄悄改写。

代码：[assessment.py](../rehab_codex_single_camera_v2_1/app/assessment.py)、[assessment_batches.py](../rehab_codex_single_camera_v2_1/app/assessment_batches.py)、[automatic_plans.py](../rehab_codex_single_camera_v2_1/app/automatic_plans.py)、[training_plans.py](../rehab_codex_single_camera_v2_1/app/training_plans.py)。

### 7.3 三种计划路径不要混用

| 路径 | 训练内容从哪里来 | 评估的作用 | 当前连接与边界 |
| --- | --- | --- | --- |
| 原自动基础活动计划 | `general-activity-rules-1`依据本人评估范围、次数及原筛查生成 | 最新同条件证据决定候选、目标与剂量上限 | 原评估／训练已接；不是病种处方或LLM自动治疗决策 |
| 原人工计划库 | 人工明确填写安排，保存plan／revision／item | 作为本人动作参考，使用时校验当前依据与契约 | 原53项目录路径；不能用动作改名兼容不同测量定义 |
| v2显式已有安排 | 使用者明确提供既有安排、次数、组数等，系统不生成剂量 | 同协议v2本人最新已提交评估提供视觉证据引用；不认定临床适用 | 肩外展／坐站／康复深蹲及左右侧；本次19项重验已在340项完整回归中，未接正式UI／APK，详见16.4–16.5 |

从算法优化角度，先分清两件事：**把动作测准**需要点、几何、时间和相位的独立参考；**让计划合适**还需要适用条件、专业依据、明确剂量和反馈政策。当前“自动生成成功”或“有完整一次”都不足以证明后一件事。

## 8. 训练、感受、进度和历史

TrainingEngine 处理 `ACTIVE／RECOVERY／RESTING／PAUSED／COMPLETE／FINISHED`；休息／暂停不参与运动计次。训练绑定计划 ID、revision、entry_key、评估参考与本次条件。

原电脑版 `summary.plan_completed` 主要按组数完成判断；质量另行报告，自评另影响继续。不能据此声称“每次都高质量完成才推进”。APK 有独立目标与继续规则，不能仅把字段同名当成逻辑相同。

疼痛、疲劳为独立 0–10 自评或空值。继续资格沿“当前条目最新训练 → 完成与来源 → 已保存自评 → blocked／next_key”判断。调度改期只修改安排，不修改训练完成或目标。

历史报告从保存快照派生。纵向比较核对人、动作侧别、来源情境、机位、模型、尺寸、基线、目标与预处理等条件。不兼容时断开曲线。当前严格签名有时连两段新录像也会判不可比，后续宜区分“测量含义契约”和“本次证据身份”，而非删掉所有校验。

有效观察比例是覆盖，不是正确率。例如电脑评估按有效观察时间／首末观察跨度计算；训练有活动时间分母；APK 无跨度时与电脑版空值语义不同。比较优化结果必须同时写清分母。

## 9. 健身动作和器械分析

### 9.1 八种动作

用户先选择深蹲、硬拉、卧推、划船、过顶推举、弯举、俯卧撑或分腿蹲。电脑以膝／髋／肘内角为主，结合躯干或上臂辅助指标，不是自动识别动作类型。

```text
progress = (angle-start_angle)/(turn_angle-start_angle)
离开起点 → 连续到达转折目标 → 返回起点带 → 完整一次
```

结果含完整／部分次数、覆盖、范围、起点／转折／回位关键帧、出程回程时间和角速度；部分动作有代偿阈值。肌肉激活、关节力矩和真实人体发力未直接测得。

APK 深蹲在特定覆盖条件下可用实际髋往返替代缺失膝计次，并记录代理来源；不能因此输出没测到的膝角或膝深度。

### 9.2 标尺、跟踪与动力学

电脑模板跟踪用灰度归一化相关匹配，检查匹配分数、歧义、时间和尺寸连续性。将标尺和参考点应用到所选轨迹，再局部拟合求导。

```text
s = 参考真实长度 / 参考像素长度                 米／像素
h(t) = [y(0)-y(t)]×s                            向上为正
局部拟合：h(t_i+τ) ≈ Aτ²+Bτ+C
v(t_i) = B；a(t_i) = 2A
F(t) = m×[9.80665+a(t)]；P(t) = F(t)×v(t)
```

这里是所跟踪自由重量的竖直外力和对应运动功率，不是肌肉力、人体总功率或关节力矩。质量 20 kg 不能替代空间标定；固定相机、近似同平面、自由重量等假设需要成立。

电脑版局部窗约 ±0.18 秒、至少 7 个点；加速度还要求约 20 Hz 和拟合残差限制，因此速度可用时力／功率仍可能缺测。APK 使用另一套中位数和局部线性求导，初始姿态抽样约 8.3 Hz，降级更低，不能与电脑峰值直接比较。

位置噪声经一次、两次求导放大，是本功能首要误差来源。器械高频跟踪应与低频人体姿态分别设计，不宜通过取消采样门槛制造“峰值”。

代码：[fitness.py](../mobile_rehab/fitness.py)、[fitness_analyzer.py](../mobile_rehab/fitness_analyzer.py)、[barbell.py](../mobile_rehab/barbell.py)、[APK motion](../android_offline/web/motion.js)、[APK barbell](../android_offline/web/barbell.js)。

## 10. 体态、日常活动、卧室与安全

### 10.1 体态

正面测肩线／髋线倾角和躯干偏离竖直；侧面测耳肩水平偏移、躯干倾角、膝内角。每个指标选连续有效片段，至少一定样本和时长，再取中位数及 MAD、覆盖率。

```text
肩线倾角 = atan2(|Δy|, |Δx|)×180/π
耳肩偏移百分比 = 100×|耳_x-肩_x|/肩髋长度
MAD = median(|x_i-median(x)|)
```

耳肩偏移当前取绝对值，不可靠区分前后方向。骨盆前倾、体表围度／体脂、脊柱逐节形态、肌少症或骨质疏松预测尚未成为现有完整测量／预测能力。

### 10.2 被动观察相关场景

| 场景 | 当前逻辑 | 保存事实 | 未完成的扩展 |
| --- | --- | --- | --- |
| 日常活动 | 髋中心、膝、躯干与 ROI 判断坐站／移动；踝交替等辅助行走规则 | 有效活动区间、任务状态 | 标定步速／步长、疾病步态分类、手机全天后台监测 |

| 卧室 | 床／床沿／出口区域，坐起→站起→出口状态链 | 可见状态、离床事件 | 被子下睡眠检测、夜尿次数自动判定 |

## 11. 健康事件、基线和趋势判断

### 11.1 输入与归一

当前指标包括步数、步速、睡眠时长、夜醒、静息心率、体重、血氧、收缩压、舒张压、血糖。入口包括手动、接受的对话事实、已配置设备适配、确认后的图片候选和合法导入。摄像头并没有测出这十类全部数据。

先验证有限值、单位、人物、时间、来源与权限，再进入 HealthEvent。事件按稳定 ID／同日同事实去重；每日同指标通常取最新测量，不是全部平均。血压要保留同测次配对，不能拿不同测次的两个值当一组读数。

日期型主诉可用当天 12:00 作为兼容表示；不等于实际发生时间。当地“今天”、ISO 日期和 UTC 偏移需专项测试。

### 11.2 当前变化公式

Detection 默认基线窗口 14 天、排除近期 3 天，至少 5 个基线日点；近期 3 天至少 2 点。

```text
μ_base = mean(x_base)
σ_base = sqrt(mean((x_base-μ_base)²))
bad_delta = d×(μ_recent-μ_base)
bad_ratio = bad_delta/|μ_base|
z_bad = bad_delta/max(σ_base, metric_min_sd)
```

`d` 是预设不利变化方向；`metric_min_sd` 是防止零方差放大微小差异的工程参数，不是医学正常值。零基线或不足样本时相应信号缺失。

DetectionEngine 再运行指标变化、情境、多信号融合和绝对安全规则；多信号按类别计分。输出 Finding，按 urgent／alert／watch／info 排序。PersonTwin 整理基线、趋势和背景，但二者数据覆盖和变化门槛尚不完全一致。

score 是规则分数，不是患病概率。负向／假设主诉的状态过滤、来源切换、离群值、跨午夜和基线覆盖是主要优化点。手环／HealthKit 适配存在，不代表红米已支持所有品牌蓝牙协议。

代码：[events.ts](../ankang/route1-health-agent/src/pipeline/events.ts)、[normalize.ts](../ankang/route1-health-agent/src/data/normalize.ts)、[baseline.ts](../ankang/route1-health-agent/src/engine/baseline.ts)、[detect.ts](../ankang/route1-health-agent/src/engine/detect.ts)、[personTwin.ts](../ankang/route1-health-agent/src/engine/personTwin.ts)。

## 12. 智能康复管家、语音、图片与资料

### 12.1 管家怎样处理信息

```text
原话 + 当前本人／上下文
 → 人物、日期、已发生／否定／假设、不确定、更正、隐私理解
 → 接受事实或澄清 → HealthEvent／原事实更正
 → 基线、Finding、任务和授权摘要重算
 → 本地回复或配置的语言模型回复 → 实际保存回执
```

ProductService 统一这些领域操作；电脑 ProductBackend 通过串行 Python→Node JSON 行桥接调用。模型未配置时仍有本地规则路径；模型回答自然不证明其记录正确。

康复只读工具提供近期评估、训练历史和计划；宿主固定 owner、来源和情境。不允许查询产生新测量，空结果不能由语言模型补造。v2 历史尚未默认接入这些旧只读工具。

### 12.2 容易混淆的输入入口

| 路径 | 处理结果 | 是否自动进入健康事实链 |
| --- | --- | --- |
| `ui.voice.transcribe`／上传转写 | 本地 Whisper 等输出文字草稿 | 否；入口本身不创建 Agent turn |
| 通用 `voice.input` | voice port 转写后交给 `chat` | 可以进入理解／接受事实；不能声称总有人工草稿确认 |
| OCR | RapidOCR／APK Tesseract 输出文字 | 否；文字正确与数值／单位正确还需区分 |
| 结构化健康图片解析 | 配置服务解析出候选，经用户确认／修改 | 确认后形成事件，保存候选和复核元信息 |

资料原件按 owner／类别保存，支持回收站、恢复和导出。资料读取得到的是原件与元信息；医学视频理解和动作录像分析不是同一条链。

## 13. 用药、安排与照护工作流

药物原名称／说明独立保存；每次服药由 `medId|date|time` 定位 taken／skipped／unrecorded。“未记录”不自动等于漏服，摄像头也没有证明吞服。

照护协调只操作允许的既有服药记录和训练改期，不自动处方、加药、改剂量或启动训练。

## 15. 持久化、队列、任务与错误恢复

### 15.1 哪个存储才是事实源

| 存储 | 内容 | 当前保证／缺口 |
| --- | --- | --- |
| `home_rehab.sqlite3` | 原康复会话、逐次、快照、任务、事件、档案和计划 | 单实例写入线程／事务；多进程仍依赖 SQLite 锁 |
| `product_daily.sqlite3` | 日常安排、逐次记录、审计、Care 回执 | 对应业务变化与 receipt 同事务 |
| `product/` JSON | 健康事件、档案、关系、通知、资料等 | 单文件临时替换和备份；无跨文件总事务 |
| `silver_support.sqlite3` | 银龄支持请求、授权和反馈 | 独立作用域与 revision |
| 手机托管 jobs | 原片、进度、result／error | 与康复 SQLite 非跨存储原子提交 |
| APK 状态与 IndexedDB | 本地业务／作业、媒体原件 | 两种存储不是同一个 SQL 事务 |
| `phone-cloud.sqlite3` | 设备、关系、备份 | token／类别权限、revision 冲突检查 |
| `rehab-v2.sqlite3` | opt-in v2 会话、操作、贡献、反馈 | 独立命名空间；不冒充旧会话 |

### 15.2 准确性之外的可靠性

原 ProductBackend 单 worker 串行处理，底层 jobs／results 队列没有总容量上限。慢模型或语音会阻塞后续产品请求。调用超时不保证正在执行的写入已经取消，重试前要查是否保存。

托管录像有文件、存储、时长、作业数和子进程限制；服务崩溃后需要核对 SQLite 与结果文件。APK 还要验证后台、熄屏、低内存和存储不足。

必须区分：请求接收、帧处理、动作确认、权威提交、报告生成、通知送达、计划继续。一个 `done` 无法表达全部。

建议对账顺序：先找权威 session／event／receipt，再核对作业或报告，最后重建可派生结果。不要为修复一份报告重复生成训练事实。

### 15.3 身份与安全

托管访问有配对／cookie 与当前 owner 绑定；APK 原生能力限制到可信本地 origin；云端辅助检查凭证、归属和类别权限。现有演示边界不等于已完成生产公网身份体系、加密、灾备和安全审计。

`lifecycle.clear` 有自己的产品清理范围，不代表所有患者库、药物、原件和备份都删除。需要按存储逐项列清理与保留清单。

代码：[storage.py](../rehab_codex_single_camera_v2_1/app/storage.py)、[ProductBackend](../rehab_codex_single_camera_v2_1/app/product/backend.py)、[JSON 持久化](../ankang/route1-health-agent/scripts/product-local-store.cjs)、[server.py](../mobile_rehab/server.py)、[APK store](../android_offline/web/store.js)。

### 15.4 失败后应恢复哪一层，而不是整套重做

| 情况 | 当前可依赖的事实／实现 | 正确核对方向 | 不能据此声称什么 |
| --- | --- | --- | --- |
| 原产品调用超时 | `ProductBackend.call` 的等待超时不保证后台操作取消 | 先查询该owner的实际记录，再决定是否重试 | “超时所以一定没保存” |
| 上传录像分析中断 | 原片、job状态／result、可能已写入的康复session是不同对象 | 对账媒体、job与SQL引用；保留来源及错误 | job文件与SQL已经跨存储原子提交 |
| APK分析或保存中断 | 本地job状态、业务状态与IndexedDB媒体分开 | 重开后确认哪些原件仍在、结果是否真实保存 | 状态为done就证明媒体和全部派生事实完整 |
| v2重复finish／丢响应 | canonical commit和操作幂等回执，finalize同事务保存事实与唯一贡献 | 查询commit；用原操作键核对或重试，不新增训练事实 | 一次HTTP响应丢失就是一次新训练 |
| v2结束已接收但尚未最终保存 | `request_finish`先保存冻结操作；HTTP202／finishing不含commit_id，后台另执行finalize | 查询commit及执行诊断；失败尝试已退出后，用原key和原载荷重试，不改结束边界 | “HTTP202就是已保存”，或接收变快表示推理变快 |
| v2宿主重启时仍为draft／finishing | 构造SessionService时先执行`recover_unfinished`；按已有检查点终结为interrupted、结清未处理帧并更新结束操作回执；16.8已实测三个特定退出窗口 | 查重启后的canonical、唯一贡献和未确认部分；不恢复半次，也不重开已finalized事实 | 三窗口TEST验证就证明突然断电、原生进程孤儿或全部异步故障都已解决 |
| v2报告资源忙／被所属抢占 | 已提交事实不变；报告写pending并由消费线程重查 | 查 `derived_report_state`、失败原因、最新feedback revision | 报告未ready就是训练没保存 |
| v2旧报告遇到新自评 | `report_state` 比较expected feedback revision，拒绝旧投影覆盖新反馈 | 重建对应最新自评的报告 | 旧报告可以回写视觉次数或自评 |
| v2资源不可用／报告超时 | 与ResourceBusy区别；正常记failed，不冒充延期成功 | 修复实际资源问题，再查事实和可重建报告 | failed表示全部训练事实回滚 |
| Care确认后重试 | 业务变化与receipt同事务，工作流保留逐步结果 | 查原idempotencyKey与receipt，重新核对expected事实 | 事务成功说明原自然语言意图一定理解正确 |
| 研究训练中断 | 已提交显式epoch恢复，绑定数据／配置／源码／数值环境并保留原run | 只用已提交恢复边界、新输出和实际退出凭据；恢复RNG／优化器／选模历史 | 已经开始test的实验还能续训；CPU工程一致性保证全部硬件或真人收益 |

v2上述报告与资源行为直接对应 [SessionService.rebuild_report](../mobile_rehab/rehab_v2/service.py)、[SessionRepository.finalize／feedback／report_state](../rehab_codex_single_camera_v2_1/app/rehab_v2/sessions.py) 和 [资源层](../rehab_codex_single_camera_v2_1/app/rehab_v2/resources.py)。其他路径的保证各自独立，不把v2的同事务事实保证推广到原产品JSON或APK存储。

v2 将指标值、valid／reason、observed／filtered／predicted、必要点、观测时间、计算时间与 age 分开。仅当前有效观测及其因果滤波参与完成；预测、过期、缺口中的转折不确认一次。


已有默认所属推理和报告进程、有界共享载荷、超时／退出确认、旧 epoch 拒收；控制和 SQL 仍在宿主。报告失败不回滚已保存事实；旧反馈报告通过 revision 比较不能覆盖新反馈。

### 16.3 部分关节标注的训练：损失、训练循环与数据资格

`d5c351f` 已提交 `pose_masked_loss.py`、`pose_masked_smoke.py` 和 TEST 工程验证。它复用锁定的原 Ultralytics 检测、框、DFL 和 TAL 分配；只调整关键点监督，不改产品安装库或生产模型。核心是区分“没标过”和“复核后确认无法定位”。

```text
第 j 个点是否明确标注：a_j ∈ {0,1}
参考 visibility：v_j ∈ {0,1,2}
坐标监督 mask：m_xy,j = a_j · 1[v_j > 0]
objectness 监督 mask：m_obj,j = a_j

e_j = 1 - exp(-||p_j-q_j||² / [2·(2σ_j)²·(area+ε)])
L_xy = mean_有可定位点的分配anchor(Σ_j m_xy,j·e_j / Σ_j m_xy,j)
L_obj = mean_明确标注槽(BCEWithLogits(z_j, 1[v_j>0]))
总损失保留原检测／DFL／gain，再合入上述关键点两项
```

`p/q` 是同一已分配 anchor 下、同一坐标尺度的预测／参考；`z` 是点 objectness logit。没有监督时使用保持计算图的零损失，不用未标点稀释分母。每个对象的点和 mask 按同一个 GT ordinal 映射，不能把人的标签与另一人的 mask 拼接。visibility 1 可有可靠坐标参考，但不等于视觉模型确信该点无误。

`pose_training.py` 实现条件式多轮训练：严格 JSON 配置与数据资格 → 分人／录制 train、val、test → 只 train 做亮度／对比度增广与 AdamW 更新 → 每轮 val 按全参考 PCK 优先、覆盖次优选模／早停 → 冻结 best → 独立 test → 模型卡。保存 last／best、优化器与 RNG，使用所属子进程、OS 单作业锁、时间和资源限制；取消请求与实际退出确认分开。子进程请求及失败写入也限于本次专用run，范围外请求不覆盖邻近文件。源码交付不等于新模型通过产品准入。

### 16.6 离线增量：采样／已知丢帧怎样影响原判断

固定相同视频／预测点／原规则，九个预声明条件改变分析采样、已知丢帧或反事实时间；不把已滤波缓存抽帧后再平滑。实际链是“原结果授权及SHA → COCO17原点／seq／媒体PTS → 本条件保留帧 → 全新原EvidenceAdapter因果EMA → 原ProtocolEngine → 主指标有效性／基线／次数／时间 → 忽略目录私有轨迹 → 非识别聚合报告”。不会写入用户历史、生成计划或部署新模型。

原EMA为`alpha=1−exp(−dt/0.12)`，虽然按时间间隔变化，输入点的顺序和数量仍会改变角度；时间常数相同不保证采样不变。主动每2／3／6帧采样不自动当队列丢帧；明确每20帧丢一帧、中部缺口和末帧丢失通过原`note_input_gap`打断连续性，不能补出隐藏回程或保持。时间原点加1000秒和固定12毫秒扰动仅为反事实测试，不是手机曝光或网络实测。

两段原缓存实际443／429帧，参考复算有效434／48；肩每6帧73/74有效、与reference共同有效73帧的角度差异p95为9.707°，深蹲每6帧7/72有效、共同7帧的p95为17.331°。这是同模型处理差异，不是金标准误差；样本少时不能解释成人群分布。`V/K`保留帧覆盖和`V/N`原帧保留覆盖分别输出，抽掉无效帧造成前者升高不代表准确性提高。

九条件×两片均没有默认稳定准备基线，均0次确认、完整时间中位数为null。因此次数相同不是稳健性证据；优先需要清晰准备→动作→回位素材及独立标注，不能降低阈值把这些片凑成成功。工程TEST轨迹另验证三动作可在原／每2／3／6帧完成，且未来点不改已有前缀、缺点／丢帧不虚构连续保持。

### 16.7 工程增量：连续输入、并发控制与最终事实对账

已提交[短时负载工具](../tools/rehab_ml/session_load_audit.py)和[三轮核验器](../tools/rehab_ml/verify_session_load.py)，复用现有认证JPEG API、`SessionService`及原所属YOLO进程，不替换生产模型或状态机。本节说明已有验收的信息链，不是新增患者功能，也不是全产品压力测试。

```text
请求：owner + session_id + event_id + seq + JPEG
 → accept_frame：校验／去重，SQL记录accepted
 → 单保留槽：旧待处理帧被替换时记录dropped及原因
 → 所属YOLO：当前有效观测 → 指标证据 → 协议／组次
 → checkpoint：该seq记processed，保存当时状态

并行pause／resume → 操作回执／revision／control_epoch
 → 旧世代结果不能回写新状态；缺口不能拼成连续保持

finish → SQL冻结受理边界／操作 → HTTP202仅表示接收
 → 单消费者有界结清在途帧
 → 同事务最终snapshot + canonical commit + 唯一计划贡献
 → 原key／新key结束重试仍指向同一事实
 → 独立自评revision → 可重建报告；不回写视觉事实

关闭所属服务 → 独立只读SQLite连接
 → 对账最终事实、逐帧状态、canonical commit及唯一贡献
```

这条链要保留三个不同数量：HTTP尝试数、SQL接收数、SQL处理数。暂停／终止后的规定拒绝不进入接收账本；接收后被槽覆盖也不等于处理成功。正式帧端接受图像，不公开信任客户端自报的关键点结果。

```text
A = SQL中本会话全部已接收seq的集合
P = 最终status=processed的seq集合
D/U/F = 最终dropped/unprocessed/failed的seq集合
终态要求：A = P ⊎ D ⊎ U ⊎ F，且没有status=accepted待结清行
HTTP200的seq集合 = A
accepted_count = |A|；processed_count = |P|
accepted_last_seq = max(A)；processed_last_seq = max(P)
persisted_evidence_seq = max(P)                 本路径当前实现
空集合高水位为-1；max(seq)不是处理数或覆盖率
排除区间展开后的(seq, reason)集合 = 所有D/U/F行的对应集合
```

`⊎`表示互不重叠的并集。seq存在空洞并不表示缺失行；先按实际接收集合对账。不可仅用“处理到第100帧”推断处理了100张图。SQL中的processed也只表示本帧完成处理／保存，不表示每个关节指标有效或动作质量合格。

### 16.9 宿主退出时，原生推理与报告怎样释放

这是F33的运行可靠性，不是角度或计次算法。原正常关闭能够终止所属worker，但宿主被强制结束后，原生计算未必及时读取通信管道关闭。隔离基线中，两个原生阻塞目标和原YOLO冷启动目标均超过预先2秒释放期限，需要监督程序清理；失败记录保留。

| --- | --- | --- |
| 精确Process与Job句柄 | 绑定后才启动原姿态／报告任务；不根据旧PID重查杀 | 宿主退出后原child句柄已收到退出信号，无监督程序补杀 |

### 16.14 独立专业标注：怎样为算法优化建立可追溯的参考

这一链属于F34离线研究工具，不是新增患者评估接口，也不会把标注、模型预测或测试夹具写入患者历史。它解决的是“与什么比较”的问题；仅凭当前模型画出的骨架或视频总评分，不能验证点、相位、计次和提示是否准确。

| 顺序与实际入口 | 收到的信息 → 实现方法 → 输出 | 后一跳需要保留的信息 |
| --- | --- | --- |
| 1：`_source_samples` | 明确下载回执 → 复核原发布版／许可、清单、原文件字节与MD5／SHA、固定按人划分 → 已核验样本与来源证明 | `sample_id`、`subject_group`、`exercise_id`、视角、协议版、`split`、原片SHA与字节；不能由相机AF猜患侧 |
| 2：`build_bundle`／`prepare-annotations` | 来源证明 → 先写规范和模板，再读取真实媒体时间 → 独立A／B／REVIEW空表、逐片PTS表、`bundle.json` | `time_basis=stream_relative_media_pts`、原时间起点、PTS与时间表SHA；不复制视频、不预填评分或预测 |
| 3：人工独立审查 | A／B分别查看原片、逐次填写 → 各自完成全片审查和动作清单 → 带身份／标注版本的JSONL | 侧别、条件、逐边界时间／mask、可观察完成、物理参考、逐问题可测性、提示机会；未知仍未知 |
| 4：`validate_record`／`differences` | 两份记录＋真实PTS → 核对值／mask、生命周期、时间顺序、数量、同源证据，逐路径列出分歧 → 待复核记录 | 分歧包含mask，不能自动平均；同一帧不能证明完整往返，整片评分不能复制成逐次真值 |
| 5：第三人专业复核／`audit_bundle` | A／B原始digest＋完整分歧 → 独立第三人填写资格、决定与逐项解决 → approved／pending／excluded | 三个不同身份、输入digest、完整队列与固定split；填了资格文字不等于完成真实人员资格核验 |
| 6：`import_reviewed`／`import-annotations` | 合格复核 → 再次验证来源与表单未变化 → `rehab-reviewed-temporal-reference-1` | 原bundle／表单SHA、已批准标签、全队列、待标／排除分母、研究用途；不启用产品、不生成姿态点标签 |

值与监督资格必须成对传递。例如`observable_completion=None`＋对应mask=false表示不知道，不是未完成；`observable_count=None`＋mask=false也不是0次。只有全片独立审查、完整清单、各次可观察完成已知、明确`observable_count_mask=true`时，0次才可作为参考。部分复核合格可导入，但其余样本仍以pending／excluded保留，不能消失或变成负例。

质量问题也分两层：`assessable`／`assessability_mask`描述这一问题在该条件下能否评价；`state`／`state_mask`描述present／absent／unknown。确认“没有问题”需要可评价证据，关节被遮住不能自动记正常。提示机会的时间窗、类别和优先级可独立标注，但`actually_received`、`later_improved`和干预证据目前必须为空；没有真实接收及后续干预证据，不能推论提示已起效。

物理完成与可观察完成是不同字段。当前实现仅支持原片可见且同源SHA一致的物理参考；隐藏的完成或外部同步参考仍需另外建立资格适配，不能通过写入任意路径接入。坐站允许不要求回坐，肩外展／康复深蹲要求可见回程与结束；这里是标注协议的任务定义，不是放宽生产计次门槛。

实际`professional-annotation-audit-3581f13f`复核原MobiPhysio3.0／CC0的24人24段肩外展、680355016字节和14／5／5划分，生成三套各24份空表及真实时间表。当前pending=24、approved=0、known_labels=0、reference_generated=false；没有专业真值，尚不能据此训练或声称准确率提高。34项专项通过，空监督导入及三个TEST篡改被拒绝。方法、字段和填写入口见[独立专业标注规范](development/REHAB_PROFESSIONAL_ANNOTATION.md)，实际边界见[本机验收](validation/REHAB_PROFESSIONAL_ANNOTATION_2026-10-12.md)。

可靠性还有实际资源前提：最终完整490项有4个空间预检错误，旧手机19项有7个507空间不足；E盘核对时仅443142144字节。D盘隔离TEST目录的整份姿态训练工程30项及旧手机19项重验通过，但没有修改空间门、迁移源录像／患者库或恢复默认E盘容量。完整回归仍为failed；不同磁盘的子集通过不能相加成全套验收。原记录见[完整回归](../reports/rehab_backend/regression.json)和[存储子集重验](../reports/rehab_backend/storage_recheck_verification.json)。

### 16.15 参考到计次／相位评价：怎样判断改动究竟改善了什么

`evaluate-annotations`是F34离线消费者，不接患者历史、正式提示或处方。独立导入reference先通过`verified_reference`回到当前原bundle、许可／源／PTS及三人复核；旧参考与新表单不一致时拒绝。当前真实0GT，实际24份空包在读取预测之前拒绝，不能自动补出准确率。

预测采用单独的`rehab-temporal-predictions-1`：实现／模型／配置SHA、原片SHA、侧别、协议、split、真实时间基础，必须保留所选val／test全队列，包括待标／排除和后端失败记录。计数和六种边界各自可用，失败为null，不填0。observed／filtered事件才能作为观测预测；未知参考不是负例。该manifest仅是声明式后端导出，尚未自动接正式trace，SHA及“不使用参考”声明不能证明实际运行或人员盲法。

| 任务 | 当前实现与输出 | 要一起核对的分母／限制 |
| --- | --- | --- |
| 可观察计数 | pred−reference；MAE、偏差、逐视频多计／漏计、准确计数视频数 | 仅独立count mask已知且预测可用才有误差；缺预测数、已知参考覆盖与完整原队列一起报告 |
| 逐边界 | 同种边界有序一对一动态规划，先最大匹配数，再最小总绝对时间误差 | 不跨类型、不复用预测；预先固定0.25秒工程容差及policy SHA，不用test反复选容差 |
| 缺标与无法评价 | 已知边界未匹配为FN；只有完整已知的边界清单才把额外预测记FP，否则unassessable | 召回、可评价部分精确率和含unknown的保守精确率下界一起报告，不能靠未知多宣称高精度 |
| 时间误差 | 已匹配pred_time−reference_time的绝对均值／中位数、偏差、p95 | 缺预测不补0时间；按人汇总，不把数千帧当数千病例；暂无受试者bootstrap CI |
| 队列与来源 | 全队列、批准／待标／排除、每人结果、输入和policy SHA | 无数据指标为null，未支持点误差、质量分类、提示干预效果、同步物理参考、疾病／剂量或手机性能 |

### 16.16 实际原RGB到计次预测：补齐声明之外的执行证据

## 17. 五个例子：把各功能之间的信息真正串起来

### 17.1 一次肩外展评估到下一项训练

| 步骤 | 传递的信息 | 如果出错，下游会怎样 |
| --- | --- | --- |
| 选参与者和动作 | participant、来源／情境、肩外展、侧别、机位 | 错人／错条件进入后续历史 |
| 模型与测量 | seq、源时间、骨架／模型、所测肩肘、value／valid／reason | 角度、转折和计次不可靠 |
| 结束评估 | session ID、范围、完整次、覆盖、结束状态、契约 | 身体汇总可能无可用依据 |
| 身体汇总 | 同作用域的最新动作／侧别证据 | 最新失败必须保留，不能偷用旧成功 |
| 自动建议 | 原评估／人物／规则指纹、筛查、范围与剂量 | 提议不能仅按一个角度复建 |
| 保存和执行 | plan ID／revision／entry_key、冻结参考 | 不能挂到另一个版本或改名动作 |
| 训练与反馈 | 新训练 session、plan_completed、质量、自评 | 做满次数不等于可继续或质量达标 |
| 历史／管家 | 保存的快照、范围限制、只读工具结果 | 查询只解释旧事实，不创造新成绩 |

### 17.2 一条健康指标到家庭摘要

原读数与来源／测次 → 单位和时间校验 → HealthEvent → 最新日值 → 足够覆盖的个人基线 → Finding／PersonTwin → 管家解释 → 类别授权投影 → 通知账本 → 渠道送达证据。

最容易丢失的是测次、当地日期、来源改变和权限。数值计算完全正确，也可能因错误日期或错人而给出错误提醒。

### 17.3 一句“已服药”到业务记录

原话 → 本人／第三人、已发生／否定、时间、用量理解 → 匹配既有 medId 与服药时点 → 待确认工作流 → 确认凭证 → 重读原说明／状态 → 事务写逐次事实和回执 → 查询回执。

自然语言语义必须在提交前正确；事务只能保证把同一操作可靠保存，不能把错误意图变正确。

### 17.4 一段健身录像到杠铃表现报告

| 步骤 | 实际传递对象 | 对准确性／可靠性的影响 |
| --- | --- | --- |
| 上传与所属作业 | 原片、job id、owner、所选exercise／side、可选barbell_calibration | 归属与动作选择先确定；原片和作业状态不等于分析完成 |
| 解码 | 原像素尺寸、seq、媒体PTS；`input_timing`记首部兼容情况 | 旋转、标尺坐标和非单调时间会直接影响角度或导数 |
| 人体分支 | YOLO→当前人物→`FitnessEngine`→summary／repetitions／series | 指标、相位、完整／部分、节奏与人体关键帧；不是器械受力或肌肉激活 |
| 器械分支 | 同一解码帧→`BarTracker`→标尺位移→局部拟合→v／a／F／P | 必须有真实长度、有效跟踪及采样；质量值不能替代标定，导数各有可用条件 |
| 结果封装 | `kind/rule_version/source_kind/usage_context/conditions/input_timing`＋两分支结果 | 器械缺测可与人体计次成功并存；不得把null补0或用人体次数代替器械上升段 |
| 查询与历史 | 所属job的`result.json`、对应作业查询／报告 | job结果不是原康复assessment；不会自动生成康复训练计划 |

先对固定原帧检查标尺／跟踪位置，再对同一位置序列检查求导，最后才核对功率；这样才能区分是像素跟丢、比例错、帧时间错还是拟合噪声。电脑和APK需要分别记录实际抽样与求导版本，不能直接比较峰值。

源码：[录像适配](../mobile_rehab/fitness_analyzer.py)、[人体状态机](../mobile_rehab/fitness.py)、[器械跟踪与分析](../mobile_rehab/barbell.py)。

### 17.5 手机上传康复录像：保存成功与作业成功分开核对

```text
POST /api/jobs → 所属原片／job → mobile_rehab.analyzer
 → 原CameraManager／VisionWorker／SceneController
 → Storage确认原康复session（REPLAY_FILE／SELF_USE）
 → 查询本人同来源历史 → build_body_profile → generate_proposal
 → job result保存session_id／summary／repetitions／proposal／input_timing
 → 作业查询与历史；保存计划后才进入对应训练路径
```

这里会先保存康复session，再写作业结果，二者没有跨存储总事务。若结果文件失败或客户端断开，先按job所属信息查实际session及结果，不能直接把原片再次分析并当新一次评估。录像建议也不能直接挂到`LIVE_CAMERA`计划：来源、情境和评估条件仍要核对。

这条链不同于实时预览`/api/live`（不产生正式训练commit），也不同于独立APK本地分析或默认关闭的v2。若用户反馈“录像处理完了却没有计划／历史”，应先找到是哪一条链的哪个保存环节未完成，而不是先换视觉模型。

源码：[康复录像适配](../mobile_rehab/analyzer.py)、[托管服务](../mobile_rehab/server.py)、[身体汇总与录像计划接口](../mobile_rehab/care.py)。

## 18. 从哪里优化：按错误层次选算法

以下是建议实验，不是已经实施的功能更改。

| 优先级 | 优化对象 | 建议比较或处理 | 必须联测的下游 | 所需参考／证据 |
| --- | --- | --- | --- | --- |
| P0 | 人物、左右、源时间、骨架和单位 | 统一契约和差分测试；旁人／换人／乱序反例 | 全部角度、计次、历史、计划 | 冻结帧、人物与时钟参考 |
| P0 | 人物／否定／日期／剂量语义 | 结构化意图、歧义澄清、提交前重验证 | 健康、照护、用药、家庭 | 独立标注原句与确认后的事实 |
| P0 | 提交与错误恢复 | 原幂等键、权威查询、版本冲突、跨存储对账 | 历史、计划进度、报告、通知 | 断响应、重试、崩溃、锁／容量实验 |
| P1 | 参考轴、起点和方向 | 稳定准备段中位数、机位约束、逐指标契约 | 范围、相位、目标、纵向比较 | 同步专业参考与独立点标注 |
| P1 | 关键点去噪 | 固定 EMA 对比速度自适应低通等 | 峰值、转折、计次、下一步延迟 | 同一参考轨迹；同时测抖动与滞后 |
| P1 | 动作状态机 | 滞回／驻留／恢复策略参数对照 | 完整次、部分次、保持与继续 | 独立阶段和起止时间标注 |
| P1 | 跨端一致性 | 同关键点／同时间测试规则，再同原片测试全链 | 电脑／APK报告、计划目标与进度 | 共享测试向量；不混采样条件 |
| P1 | 器械求导 | 先标尺／跟踪，再比较拟合窗和导数方法 | 速度、力、功率、逐次表现 | 已知运动轨迹或同步参考设备 |
| P2 | 健康个体基线 | 来源分层、均值／标准差对比中位数／MAD | Finding、PersonTwin、通知 | 离群／换设备／缺日和事件标签 |
| P2 | 质量模型与姿态微调 | 在有许可同域标签上对比规则、简单基线、时序模型 | 质量提示；上线前保持 shadow | 独立专业复核、按人隔离测试 |
| P2 | 计划决策 | 专业适用模板、明确剂量／停止规则、反馈审核 | 计划及训练继续资格 | 指南适用条件与专业审核；不能只靠视觉 |
| P2 | 性能和长期运行 | 有界队列、慢任务隔离、时延／功耗／存储压力 | 可用覆盖、指导及时性和保存 | 目标手机、真实负载、长时间测量 |

不建议第一步就换一个更大模型。先回答“点错了、角度定义错了、相位错了、资格错了，还是保存错了”，才能把算力和标注花在正确位置。

## 19. 怎样证明优化提高了准确性和可靠性

### 19.1 分层评价，不合并成一个准确率

| 层 | 应比较什么 | 参考方式 |
| --- | --- | --- |
| 关键点 | 覆盖、像素／归一误差、PCK、左右混淆 | 独立人工标点／可见性；参考图像身份严格一致 |
| 角度 | MAE、偏差、分位误差、视角／动作分层 | 与指标定义相容的专业参考；同步采集 |
| 次数与阶段 | 次数误差、完整／部分 precision／recall、转折时间差 | 双人独立标注并复核 |
| 质量 | 每个代偿项敏感度、特异度、无法评价比例 | 专业人员逐项复核，而非笼统“姿势正确” |
| 器械 | 位置／速度／加速度误差、丢跟率、峰值偏差 | 标定轨迹或参考设备；明确自由重量假设 |
| 健康语义 | 人物／日期／否定／数值单位正确、危险意图误执行率 | 原句与实际保存事实的独立对照 |
| 风险／提醒 | 漏报、每小时／天误报、触发与响应延迟 | 独立事件及适用人群结局；不以演示代替验证 |
| 持久化 | 重复事实数、丢失数、冲突、未确认提交、恢复时间 | 可重现故障注入和独立重开查询 |
| 性能 | 排队、解码、推理、规则、保存、总延迟 p50／p95 | 实际目标硬件与真实负载；区分冷启动 |

### 19.2 可直接采用的评价口径

```text
参考可定位点集合 J；其中有效预测点集合 C
coverage = |C|/|J|
point_error_j = ||prediction_j-reference_j||₂
PCK_all(τ) = Σ[j∈C, error_j/scale_j≤τ] / |J|
PCK_covered(τ) = 同一分子 / |C|

angle_MAE = mean(|θ_prediction-θ_reference|)     同一测量定义、有效配对样本
count_MAE = mean(|count_prediction-count_reference|)
precision = TP/(TP+FP)；recall = TP/(TP+FN)
误报负担 = 假报警数／实际观察小时数
端到端延迟 = 对应结果可用时刻 - 本路径定义的输入时刻
```

无预测应降低覆盖与 PCK_all，不能删掉困难样本后只报覆盖样本误差。空分母保留 null；confidence、valid_ratio、两模型一致性和单元测试通过率都不是临床准确率。

关键点参考、人体框尺度和阈值必须冻结；分人／录制划分 train／val／test，标准化与参数选择只用 train／val，test 不反复调参。视频帧随机分割容易让同一人的近邻帧泄漏到测试集。

### 19.3 最小实验记录

每次只改变一层，保留：代码提交、模型／算法版本、输入 hash、权限、人物／动作／视角、骨架／坐标／单位、源时钟、参数、参考标注版本、覆盖和排除原因、原始逐帧结果、最终事实／回执、时延与失败日志。

第一轮建议用一个肩动作跑完整康复链、一个坐站或下肢动作、一个器械录像、几组健康语义反例，再补断流／换人／丢响应／重开验证。目的是验证所有交接层，而不是一次追求全动作高分。

### 19.4 实际排错：找到最早偏离参考的那一跳

以下是建议的只读排查顺序，不表示这些诊断字段已经全部形成统一账本。原产品、APK 与 v2 输出不同，先选定一条路径，不跨路径拼凑一次“成功”。

| 顺序 | 核对输入与输出 | 最早发现偏差时，优先检查 | 暂时不要做什么 |
| --- | --- | --- | --- |
| 1. 帧身份 | 原文件／图像 hash、帧 seq、尺寸、源时间、source_kind、本人 | 解码时间、旋转／裁切、采样、迟到帧和作用域 | 用处理耗时补源时间，拿另一帧的标签比较 |
| 2. 人物与点 | 同帧独立标点 vs 原 `xy/conf`；人物框、左右和骨架 | 焦点抢占、模型遮挡误差、点顺序、坐标变换、镜像显示 | 先改计次阈值；把 confidence 当误差概率 |
| 3. 滤波与指标 | 原点 → 滤波点 → `value/valid/reason` | EMA 延迟、缺口重置、必要点、参考轴／机位与起点 | 把旧点保持当当前观测，补零掩盖无法测量 |
| 4. 阶段与指导 | 同一有效指标序列 → 相位、转折、完整／部分、下一步 cue | 滞回、驻留、连续性、坐站重置、晚结果和 cue 冷却 | 只修提示文字，或为了匹配预期次数而取消证据条件 |
| 5. 保存事实 | 结束快照／逐次 → session／canonical commit／receipt | 幂等键、版本、未确认提交、SQL 与 job 文件对账 | 超时后直接重复创建记录；报告失败就重做一次训练 |
| 6. 计划与进度 | 最新评估依据 → 提议 → 保存计划 → 本条目最新训练／自评 | 来源、过期证据、计划 revision、条目身份、完成与反馈政策 | 把高质量缺测写成正常，或用旧成功覆盖新失败 |
| 7. 报告与分享 | 权威事实 → 派生报告／管家投影 → 授权摘要／渠道状态 | 旧缓存、反馈 revision、字段转换、权限和真实送达证据 | 回写旧事实配合报告；本地显示后声称家属已经收到 |

跨端比较建议做两遍：先把**同一关键点与源时间序列**送进两套规则，隔离几何／状态机差异；再用**同一原录像**分别走两条视觉链，测模型、采样和性能带来的新增差异。前者是规则契约比较，后者才是该输入条件下的全链比较。

镜像要在坐标契约中核对：电脑画布有原图到显示、显示点击回原图的映射，解剖学左／右不能随屏幕位置重命名；标尺、ROI、关键点若来自不同坐标空间，数值稳定也可能一直测错。相关入口：[geometry.py](../rehab_codex_single_camera_v2_1/app/geometry.py)、[画布映射](../rehab_codex_single_camera_v2_1/app/ui/widgets.py)。

## 20. 当前需要团队决定或补齐的条件

1. 哪些输出只要求二维观察，哪些必须与临床测量对应；先冻结名称和参考定义。
2. 主要目标人群、姿势、遮挡和辅助器具；它们决定模型训练域和适用条件。
3. 真人视频的分析／训练授权及独立专业标注；已有分析录像不自动获得训练权限。
4. “高质量完成才推进”的确切规则：缺测时允许继续什么、不能宣称什么。
5. 三端哪些算法契约必须一致，哪些允许按性能降级；降级须保留结果来源和能力边界。
6. 计划的专业依据与审核角色；视觉测量不能替代病种适用性和治疗决策。
7. 家庭通知的真实渠道与响应责任；本地记录不等于已完成救援。
8. 正式上线的隐私、持久化、备份恢复、硬件和负载验收范围。

建议先完成“同一输入、同一测量定义、可追到原事实”的闭环，再比较新模型。否则输出数字变稳定或页面变顺畅，也无法判断究竟提高了哪一层的准确性。

## 22. 算法优化：可比较的公式、所需证据和下游影响

本节是供你决策的实验设计，**尚未在本轮替换任何算法**。同一实验先冻结输入、参考和协议，只改一层；不要同时换点模型、改角度定义、放宽计次和改完成政策，否则无法归因。

### 22.1 起点与幅度：先减少参考错误

可以比较原参考建立方法和“稳定准备片段的中位数＋离散度”方法：

```text
θ_base = median(θ_i)，i 只来自有效、同人物、同机位的准备段
dispersion = median(|θ_i-θ_base|)
稳定条件 = 有效连续时长达标 AND dispersion 小于冻结门槛
```

角度差要用对应的 wrap／方向约定。若原始参考有偏差，后续相对幅度也会偏；原姿势本身不正确，中位数仍会稳定地得到错误起点。因此起点姿势、时间和机位需独立标注。坐站须确认坐姿，而非把首次站姿当成坐姿参考。

联测范围、峰值、相位、次数、目标、历史可比性和计划依据。门槛只在验证集调整；不能用现有两段回放“必须数出几次”反推门槛。

### 22.2 关键点滤波：去噪和提示延迟一起评价

原 EMA 使用固定时间常数。可比较速度自适应低通：

```text
α(fc,Δt) = 2π·fc·Δt / (1+2π·fc·Δt)
v_raw = (p_t-p_(t-1))/Δt
v_filtered = α(fc_velocity,Δt)·v_raw + (1-α)·v_previous
fc_position = fc_min + β·|v_filtered|
p_filtered = α(fc_position,Δt)·p_t + (1-α)·p_previous
```

这是候选公式；`fc` 单位 Hz，`β` 必须与坐标和速度尺度配套。像素版换分辨率后不应直接沿用同一 β；速度分母使用真实源时间，不用耗时。缺点、换人、暂停、非单调时间和长缺口的重置契约先固定，预测不转成观测。

评价静止抖动、峰值衰减、转折滞后、次数误差及下一步指导延迟。只看轨迹更平滑，会漏掉“用户已回位，系统仍提示保持”的问题。

### 22.3 计次与指导：相位确认优先于提示措辞

先冻结动作各相位定义和参考边界，再比较进入／退出两套阈值、驻留时间、有效段持续性及重新准备策略。降低驻留可能减少延迟，也可能增加噪声触发；补帧可能使曲线完整，却可能凭空补出缺口中的转折。

建议逐次标注起始、转折、回位、完成／部分／不可判、允许的扶手等变式；把换人、遮挡、半次、连续快动作和站姿进入坐站作为独立反例。指导消费确认相位，分别测提前提示、迟提示、错误纠正、重复播报和取消后旧提示。

“做满组次”“幅度达到目标”“质量被观察且达标”“用户反馈允许继续”应四项输出。若后续要改为高质量次数推进，先定义并审核新政策，不能把质量缺测自动作失败或自动作正常。

### 22.4 器械速度与功率：先测跟踪误差，再选求导方法

中心差分可用于说明误差传递，不是替换当前局部拟合的指令：

```text
v_t ≈ (h_(t+1)-h_(t-1))/(2Δt)
a_t ≈ (h_(t+1)-2h_t+h_(t-1))/Δt²
位置误差对速度的影响量级 ∝ σ_h/Δt
位置误差对加速度的影响量级 ∝ σ_h/Δt²
δF ≈ (g+a)·δm + m·δa
δP ≈ v·δF + F·δv                         一阶近似
```

可比较现有二次拟合窗、稳健拟合和不同抽样率，冻结标尺、负载质量、相机平面与原轨迹。加速度峰对采样／丢跟尤为敏感；真实录像总 FPS 不等于有效跟踪采样率。

分别输出位移可用、速度可用、加速度未知、力／功率未知。评估轨迹位置误差、丢跟率、速度／加速度误差及峰值偏差；不以补满曲线或 20 kg 输入证明力学结果正确。

### 22.5 健康基线与语义：来源、事实状态先于统计模型

基线先按本人、来源和单位分层，再比较现有均值／标准差与稳健统计：

```text
μ_robust = median(x_base)
σ_robust = 1.4826×median(|x_base-μ_robust|)
z_robust = d×(median(x_recent)-μ_robust) / max(σ_robust, σ_floor)
```

1.4826 是常见正态尺度换算系数，不会把分数变成患病概率；`σ_floor`、覆盖和触发门槛仍需验证。稳健基线也不能修复错人、否定句入库或日期错误。

语义可先形成待验证命令：人物、已发生／否定／假设、事件日期和时段、原 medId／planId＋revision、用量偏离、隐私、受限证据引用。人物和时间有歧义则澄清；业务执行前再核对原说明与事实。不要把异常用量陈述压成普通 taken 记录，也不自动改处方。

联测原句理解、实际落库、日数据、Finding、PersonTwin、任务与家庭摘要。语义准确率与事务可靠性分别评价；JSON 结构正确不等于陈述含义正确。

### 22.6 姿态微调：训练指标改善后，还要验证动作链

先在独立参考上测原模型；按人／录制分组，分层覆盖动作、视角、辅助器具与遮挡。独立标点复核误差也要记录；临床参考若测的是另一个角度定义，不能直接用来评价图像投影。

候选至少同时报告：全参考 PCK、有效覆盖、覆盖点误差、左右混淆、逐关节／视角结果与失败例。选模用 val，冻结后用独立 test；反复据同一个 test 改模型就不再是独立验证。

关键点变好后，再固定原规则比较角度、计次、质量、下一步提示和计划。点级 PCK 不能代替患者功能改善或康复计划适用性；上线需单独确认骨架、坐标、模型版本、性能、降级与回退。

### 22.7 资源与时效：算得对但来得太晚，也会影响可靠性

当前保留电脑视觉最新帧槽、托管作业队列与所属子进程、v2单活动会话／单保留帧槽／控制槽和姿态训练器原单作业锁。后续新增同checkout的合作式准入：v2正式会话／原生推理共享锁，实际pose／IRDS训练、masked smoke、YOLO回放、MP VIDEO与原参考YOLO child独占锁；冲突立即拒绝，实际退出才释放，暂停／在途／隔离期间保留保护。正式忙时不启动这些离线重计算，重任务忙时不新建正式草稿；历史幂等回执仍可查询。

本轮把报告拆成“主锁短暂独占预检＋后台共享工作锁”。正式／离线重任务忙时，默认v2报告在序列化和spawn前延期；已准入报告不长期持主锁，新正式会话可开始，并请求取消同宿主准确所属报告。报告线程确认退出后才记抢占，CAS写pending，0.5秒或唤醒后再查；外部宿主已有报告和可信本地callable不能被硬取消。报告child再次预检，避免宿主准入和实际child工作之间的竞态；重任务仍需两锁独占，不能与报告并行。

信息链为`已finalized快照／回执／唯一贡献＋feedback_revision → 单报告槽 → 资源准入 → 默认child＋内容核对 → 原反馈CAS ready`。容量忙／已确认抢占只改派生pending；新反馈先写入则旧报告响应pending_newer_feedback，不覆盖新版；资源不可用／超时为failed，SQL保存错误不能称已保存。事实／次数／计划贡献都不因报告延期倒退，诊断计数也不加入事实摘要。

这不是全产品共享算力协调器。旧桌面／旧live／APK、全部下载／预处理／评估／非v2报告导出、其他checkout／机器与旧版本已运行进程尚未覆盖；短暂报告预检仍可能让新create立即冲突，文件系统／OS调用也没有硬截止。已有单机工程控制结果不能证明高负载或真人输入稳定，指标准确性未因此提高。

建议在不改变动作含义的前提下单独比较三类控制：

1. **输入背压**：实时优先当前帧，录像按可信源时间处理；丢帧、等待和无法评价分别记录，不把降采样后的有效比例当原录像全覆盖。
2. **任务隔离**：控制／提交路径不排在模型下载、训练、录像批处理和报告导出后面；重任务拒绝／延后需有明确状态，取消请求与实际进程退出分开。
3. **能力降级**：先减少分辨率、姿态抽样率或并发，并保留实际配置与能力；不要以放宽源年龄、补预测或降低计次条件掩盖算力不足。器械加速度尤其需要独立检查采样条件。

在有可信输入时钟的同一路径内，分别量化：

```text
结果年龄 = 结果可消费时刻 - 该路径定义的输入时刻
控制延迟 = 控制回执可用时刻 - 控制请求发起时刻
保存延迟 = 权威提交确认时刻 - finish 请求发起时刻
报告延迟 = 对应版本报告可用时刻 - 权威提交时刻
```

不能直接相减手机和电脑各自的 monotonic。v2 当前 JPEG 用宿主接收时刻，结果年龄不含手机曝光前后的全部网络开销。第16.7节已有原模型、连续输入和并发结束的单机短时ASGI证据；它补上输入快于推理的对账场景，但不是socket网络、真人输入或长时运行。最新独立[冷启动专项](development/REHAB_ASYNC_FINISH.md)证明该负载下结束接收不等待原模型，最终保存仍约2秒，不称推理提速。目标手机后台／熄屏、多客户端、持续功耗／内存和完整物理故障仍待实验；覆盖、次数与保存必须联测，不能只优化平均推理耗时。

### 22.8 误差怎样从关键点传到计次和计划

先把误差分成三类：测量定义不同、观测点不准、信息在传递时丢失。更好的关键点模型主要解决第二类，不能自动修复另两类。

对第5节的三点角，令 `u=A-B`、`v=C-B`。在骨段不退化、扰动较小的条件下，可以用以下一阶量级理解角度对点误差的敏感性；它不是当前代码自动计算的置信区间：

```text
δu = δA-δB；δv = δC-δB
|δθ| ≲ ||δu_perp||/||u|| + ||δv_perp||/||v||       弧度，一阶近似
角度制误差 ≈ 弧度误差 × 180/π
```

`perp` 表示相对该骨段方向的垂直扰动。中间关节点 B 的误差同时影响两条向量；投影骨段越短，同样的像素偏移越容易造成大角度误差。例如单条100像素骨段受到10像素垂直扰动，其方向变化约为 `atan(10/100)=5.7°`；这只是几何示例，不是项目的实测误差。侧位遮挡、远距离和手指短骨段尤其需要单独验证。

| 误差所在层 | 如何传给下一层 | 优化后必须再看什么 |
| --- | --- | --- |
| 人物／左右／坐标空间错 | 几何公式即使正确，也是在计算另一人或另一侧 | 人物连续性、解剖学侧别、镜像与ROI／标尺映射 |
| 点的抖动、偏差或短骨段 | 原角度抖动、参考轴偏移、某指标无法测量 | 点误差与覆盖、角度误差、无法测量原因 |
| 起点偏差 | 相对幅度整体偏移；自动方向建立也可能变化 | 起点参考、方向、范围及可比条件 |
| 滤波滞后 | 转折／回位晚确认，保持区间和下一步指导延迟 | 峰值损失、相位时间差、提示迟早，而不只看平滑度 |
| 阈值附近的角度偏差 | 跨过或没跨过转折带，完整次变部分次或漏次 | 完整／部分误判、次数误差、驻留与缺口边界 |
| 范围／计次／覆盖变化 | 原自动建议可能改变候选、目标、次数或准入结果 | 同一证据进入 `generate_proposal` 后的差异；不只比较最终角度 |
| 保存或投影丢字段 | 历史、管家或进度看到的不是引擎实际结果 | 原快照、权威回执、计划版本、来源与报告版本对账 |

原自动目标在未触发上限等分支时，增大型为 `T=0.2·low+0.8·high`，减小型为 `T=0.8·low+0.2·high`。因此目标误差也会继承上下界误差；若是否达到15°范围、覆盖0.8或完整一次的工程准入发生变化，输出还会出现分支跳变。实际代码仍需检查上限、日期、测量契约、筛查和反馈，不能仅用这两个线性式复刻完整建议。

电脑器械链有类似放大：位置→速度→加速度→外力／功率，见22.4。健康链则可能是人物／日期／来源错→日数据错→基线错→提醒错。优化时沿着最早偏差向下追，不要只调整最后的文字或阈值。

### 23.1 三份相互独立的验收包

| 验收包 | 最小内容 | 产物 | 判定什么 |
| --- | --- | --- | --- |
| 规则契约差分 | 同关键点、同源时间、同动作／侧／目标，输入电脑规则和 APK 规则；覆盖缺测／暂停／换人 | 逐帧指标、相位、次数、目标与继续状态差异表 | 跨端差异来自规则还是视觉模型；不主张端到端真人准确率 |
| 真人独立参考回放 | 一个肩动作、坐站或有适用计划的下肢动作；准备、半次、遮挡和扶手变式；明确授权与独立复核 | 原片身份、标注版本、覆盖、逐次／阶段误差、错误样本 | 真实动作是否被正确观察；未标部分不能补成金标准 |
| 权威事实及恢复 | 丢响应后重试、暂停期间晚结果、finish 重复、报告失败、锁／容量／重开；只用隔离库 | commit／receipt、唯一贡献、报告 revision、恢复过程及 hash | 不重复、不丢失、不混人、不把失败称成功；不替代断电／实机压力验证 |

若暂时没有真人参考，可以先完成第一和第三包；第二包状态保持未验证。已有自拍视频能做授权分析回放，不能自动充当独立训练标签。

### 23.2 每个实验至少回答八个问题

1. 改了哪一个模块、哪个参数，源码／模型／协议版本是什么？
2. 输入来自哪里，分析与训练权限分别是否成立？
3. 独立参考是谁提供、怎样复核，测量定义是否相同？
4. 人物／录制怎样分组，调参是否使用了测试集？
5. 误差、覆盖、无法评价和失败分别是多少，分母是什么？
6. 相位、计次、质量、继续资格和最终保存有哪些下游变化？
7. 在目标手机或电脑的冷／热／低性能条件下，延迟和故障表现如何？
8. 候选拒绝、取消、存储错误或服务重启时，能否回到权威事实并安全重试？

算法优化的目标是让有效输入得到更准确、可解释、可恢复的结果。让提示更少、数值更齐或界面更顺，不应通过丢弃困难样本、补造缺测、取消身份和提交校验来实现。

### 23.3 本文件的维护方式

每次实现更新同时记录功能状态、真实字段、依赖、实际验证run／版本和仍缺的证据。历史结果保留原范围，不累计成最新测试数。本轮安排／质量参数的实现及实际回归见 [本轮验收](validation/REHAB_BACKEND_PLANS_2026-10-11.md)。[此前算法交接核对](validation/BACKEND_OVERVIEW_ALGORITHM_HANDOFF_2026-10-11.md)、[此前功能链核对](validation/BACKEND_OVERVIEW_FUNCTION_CHAINS_2026-10-11.md)、[此前依赖核对](validation/BACKEND_OVERVIEW_DEPENDENCIES_2026-10-11.md)、[此前参数核对](validation/BACKEND_PARAMETER_MAP_2026-10-11.md)、[此前可靠性核对](validation/BACKEND_OVERVIEW_RELIABILITY_2026-10-11.md)及其他历史记录保留当时基准，不作为本次重新运行的证据。

### 24.2 改算法时，哪些责任不能顺手改变

| 本次只改的层 | 应保持不变 | 否则无法判断改善来自哪里 |
| --- | --- | --- |
| 关键点模型 | 输入原片／帧身份、坐标空间、骨架映射、原几何和规则 | 点质量、机位适配和放宽计次混在一起 |
| 滤波／准备参考 | 原点输入、人物／时间、角度定义、原相位阈值 | 轨迹更顺与动作更容易判成功混在一起 |
| 几何公式／机位 | 点输入及参考标签身份；明确升级测量契约 | 新旧指标其实测的不同量，却比较所谓误差下降 |
| 相位／计次规则 | 同指标序列、计划目标、完成／部分标签及保存机制 | 阈值放宽与患者高质量完成混在一起 |
| 提示策略 | 已确认动作事实、下一步语义及计划 | 提示改变反过来补造动作完成 |
| 健康基线 | 已验证的原事实、单位、来源与授权 | 错人／否定入库的问题被统计平滑掩盖 |
| 存储／任务协调 | 计算快照、原幂等键、计划绑定、反馈版本 | 重建报告或重试任务变成再次贡献训练进度 |

这些是实验隔离原则，不是要求永远不能改政策。如果团队决定改变目标、质量推进或来源兼容性，应另列政策版本、适用范围和迁移验证，不能藏在模型或滤波参数更新里。

## 25. 将准确性与可靠性变成可选的后端改进任务

这一节是后续方案，不是本次已经改好的功能。前面的章节回答“现在怎么实现”；这里回答“发现哪类错误后，下一步改什么、怎样知道改好了”。

### 25.1 先做定位实验，再选优化方案

| 观察到的问题 | 第一份对照实验 | 找到偏差后的候选改动 | 验收要同时保留什么 |
| --- | --- | --- | --- |
| 肩／膝角波动或偏小 | 固定原帧和人工点，分别计算原点、模型点下的同一几何 | 模型／坐标变换、机位参考或滤波，按定位结果只改一层 | 点误差、角度偏差、覆盖、转折时差；无法测量样本不删 |
| 回位了仍提示上一阶段 | 固定指标序列，对照人工相位和系统确认时间、cue时间 | 驻留／滞回或指导冷却；不通过文字修正伪造阶段 | 完整／部分、提示提前／迟到、短缺口及取消后旧提示 |
| 旁人入镜后记录串人 | 冻结两人交错／出入画序列，标注当前应跟踪的人 | 焦点匹配、丢跟恢复和人物切换重置 | ID切换、错人有效时长、基线重置和历史归属 |

| 训练做完但不能继续 | 对照条目最新session、组次完成、自评与progress | 修计划版本／条目绑定或状态映射；不默认替用户填自评 | 完成、质量、反馈、blocked原因和next_key逐项一致 |
| 杠铃速度／功率跳变 | 固定标尺、参考轨迹及真实帧时间，先比较位置再比较导数 | 跟踪分辨率、拟合窗、有效采样检查，最后才改求导 | 丢跟、位置误差、导数误差、残差、空值及峰值偏差 |
| 健康提醒不合实际 | 原句／原读数→实际事件→日值→基线→Finding逐跳对照 | 先修人物／日期／否定／来源；输入正确后比较稳健基线 | 原事实准确、单位／测次、缺日、私密投影和误报负担 |
| 保存后历史不一致／重试重复 | 在隔离数据上丢响应、重复finish、报告失败、重开查询 | 幂等、事务／版本、跨存储对账、派生重建 | 权威事实数、唯一贡献、receipt、反馈revision和原件完整性 |
| 手机发热后体验变差 | 同手机、同原片分别测冷启动和持续运行，记录实际抽样 | 降分辨率／抽样、隔离慢任务或有界队列 | 时延、覆盖、计次、器械可用性、功耗与保存；不放宽证据条件 |

这张表的“候选改动”不是承诺全部都需要做。如果同一原点输入下角度已经正确，优先查模型和坐标；如果指标正确而相位错误，换更大视觉模型往往不能解决根因。

### 25.2 可信度不应只剩一个confidence

目前原Metric只有值、valid和reason；v2额外区分证据来源及年龄，尚未形成全产品统一的数值误差区间。后续可在不改动原测量事实的前提下，新增**独立的可靠性评价产物**，再经过契约适配供计划／报告读取。

先用独立标点检验模型分数是否与误差相关，而不是直接将0.8写成“80%准确”：

```text
在固定关节／视角／尺度下，按模型confidence分箱为 B_k
参考误差 e_j = ||预测点_j - 参考点_j|| / 冻结人体尺度_j
q_k(ε) = 箱内 e_j ≤ ε 的有效配对点数 / 箱内有效配对点数
另报未检出／不可定位数、全参考覆盖和各箱样本数
```

这是建议的经验对照，不是当前已经校准的概率；空箱的比例留null，没有预测的点不能悄悄排除出总体覆盖。`ε`、分箱和分层先在train／val确定，test只做冻结检验。手部SDK没有每点confidence时，不能填一个常数冒充同等置信证据。

对下游至少保留以下互不替代的判断：

1. **当前能否计算这个指标**：必要点、有限值、骨段长度、坐标和时间合格。
2. **这类条件下测量通常偏差多大**：来自独立参考和分层实验，不来自模型自证。
3. **是否足够连续以确认这一次动作**：转折、回位、驻留和缺口按冻结协议判断。
4. **是否符合计划使用／继续条件**：依赖原评估、版本、筛查与真实自评。
5. **这次结果是否已经保存**：依赖权威session／commit／receipt；报告和通知另有状态。

改善体验可以让普通缺测提示少打断，但计算层仍保留原因和分母；用户允许启动与系统能够给出有效测量是两回事。不能通过将未知改成正常来换取计划顺畅。

### 25.3 一次优化的下游对照产物

建议每次实验输出一份机器可读对照和一份可阅读结论。以下字段是建议的实验产物，不是现有统一API，也不要求修改正常患者库。

| 对照层 | 最少保留 | 用来判断什么 |
| --- | --- | --- |
| 输入 | 原片／帧／事件ID和hash、owner／participant、采样时间、权限、固定划分 | 是否真的是同一份可比较输入 |
| 原始算法 | 原点／事件、滤波前后、value／valid／reason、分层误差与覆盖 | 改善发生在哪一层，困难样本有没有被删 |
| 时序动作 | 相位边界、完整／部分、目标／质量、cue及其时刻 | 点更准是否真的带来计次和指导改善 |
| 决策 | 最新依据ID、proposal候选／排除、target／dose、plan版本、progress／反馈 | 是否意外改变建议、剂量、继续资格 |
| 最终事实 | 原快照与保存事实、commit／receipt、唯一贡献、反馈revision | 是否重复、丢失、错人或串版本 |
| 派生输出 | 报告对应的事实／反馈版本、管家只读投影、家庭类别授权与渠道状态 | 是否解释同一事实且没有越权或假送达 |
| 运行条件 | 目标硬件、模型／软件版本、实际分辨率／抽样、冷热时延、失败与恢复 | 该改进能否在目标手机或电脑持续运行 |

没有独立参考时，可以先证明接口、规则差分和恢复正确；“真人测量更准确”保持未验证。没有目标手机实测时，可以报告电脑的计算耗时，但不能外推手机帧率或长期功耗。

### 25.4 建议推进顺序与停止条件

| 批次 | 后端交付物 | 进入下一批的依据 |
| --- | --- | --- |
| A：契约与恢复 | 同一输入的字段／时间／人物对照，跨端规则差分，权威事实与报告对账 | 所有已选案例可追到原输入；错误没有被补值掩盖；重试不重复贡献 |
| B：测量与相位 | 一个肩动作和一个功能／下肢动作的独立参考、起点／滤波／相位对照 | 同测量定义下误差与覆盖同时比较，计次／提示／计划没有未解释退化 |
| C：器械与健康 | 器械参考轨迹、健康语义反例、基线分层实验 | 导数可信条件明确；错人／否定／时间等语义问题不靠统计掩盖 |
| D：模型与部署 | 有许可同域标注、冻结选模、目标手机负载、shadow与回退方案 | 候选相对原模型和简单基线有独立证据；旧历史契约与失败回退可核查 |

具体误差、覆盖、时延目标由团队按功能和硬件先约定，不把本文工程阈值当临床金标准。遇到参考定义不一致、授权不足、测试泄漏、结果无法复现或下游事实不一致，应停在当前批次查原因，而不是继续调最终展示值。

用于讨论的最终问题是：**要让哪一条结果更可信，最早的误差在哪里，改动后哪些消费者会受到影响，又用什么独立证据证明改善？** 前24节的源码、公式和交接表，以及本节的对照产物，分别对应这四个问题。

### 26.2 怎样选择参数，而不是凭效果“调到能过”

建议对同一固定输入做单层配对实验：

```text
固定授权原片／帧、独立参考、人物及录制划分
       │
       ├─ 原参数 → 点／指标／相位 → 原下游计划、进度与保存结果
       └─ 候选参数 → 点／指标／相位 → 同规则下游计划、进度与保存结果
                         │
                         ▼
       分层误差 + 全参考覆盖 + 无法评价 + 计次差异 + 提示延迟
                  + 目标／资格差异 + 运行与恢复结果
```

先在train／val选择候选，再冻结候选、比较范围与评价口径，只用独立test核查一次。划分按人和录制，不将同一人的相邻帧随机分到两边。涉及计划剂量、继续资格或测量定义的变化另列政策／契约版本，不伪装成单纯模型参数调整。

选择时使用多个约束，不把它们加权成一个可以抵消严重错误的总分：例如角度误差下降，但错人增加、覆盖降低或重复贡献出现，仍应先解释退化。没有独立参考时，只能得出“输出改变／链路稳定”，不能得出“更准确”。

### 26.3 第一轮讨论可直接落到三个后端问题

1. **肩外展数值是否正确？** 在相同帧上分别用独立参考点、模型原点和滤波点计算同一个肩角，比较点误差、角度偏差、峰值与可测覆盖。先定位模型／机位／滤波中的最早偏差。
2. **数值正确后，动作和下一步是否正确？** 固定指标序列对照人工相位、完整次数和cue时刻；再核对评估范围、建议目标、原计划版本、训练反馈和进度。只改已定位的阶段或指导层。
3. **这份结果能否可靠保存、重试和解释？** 在隔离数据中检查丢响应、重复提交、报告失败、重开和新自评；确认权威事实、唯一贡献、反馈版本及只读投影一致。不要通过重复分析生成第二份完成事实。

这三项产物分别是测量对照、动作／决策对照、事实／恢复对照。它们接上之后，再决定是否需要更大的模型、同域微调或跨端统一，而不是先更换模型再寻找问题。

### 26.4 参数交接：实现了规则，不代表每个入口都在使用

参数要沿“请求接受字段 → 校验／归一 → 保存计划 → 本次冻结值 → 指标证据 → 判定 → 报告／进度”逐跳检查。仅在某个引擎里搜索到参数名称，不足以证明它在用户当前入口生效。

| 当前具体交接 | 实际源码状态 | 对优化的影响与核对方法 |
| --- | --- | --- |
| 显式计划的安排字段 | `BackendPlans.SETTINGS`接受`target_reps`、`target_sets`、`target_angle_deg`、`rest_between_sets_s`、`timing_plan`、`needs_companion`、`use_of_hands`及下面两质量字段 | 比较保存条目与训练`frozen_plan.plan`；客户端额外剂量或限值并不改变保存条目，不能靠请求覆盖来调参 |

对团队而言，优先把问题分类：**点或角度偏了**，查测量；**动作阶段错了**，查状态机；**有规则却没生效**，查字段和冻结；**计算正确但历史不一致**，查事实保存和版本。四种问题需要不同的实验，不能都归因于模型准确率。

## 27. 优化联测清单：让一条结果从输入一直追到消费者

前面的功能表回答“后端有什么”，函数和参数表回答“在哪里改”。本节将它们落到可执行的对照案例：改算法之前先固定输入与参考，改完以后不仅看一个分数，还要检查结果是否正确传到评估、计划、历史、管家或家庭。

以下是**建议的隔离实验**，不要求给正常患者库补写记录，不是新增统一API，也不是本次已经执行的实验。无独立参考时，只能判断输出差异或工程可靠性，不能判断人体测量更准确。

### 27.1 肩外展：把模型误差、几何误差和动作误差拆开

对应F06–F17。在同一获准原片、同一人、同一侧、同一机位下，保留实际PTS、原尺寸及模型版本；由独立标注得到所需点和动作阶段参考，不拿模型预测回填参考。

| 要核对的一跳 | 固定输入与计算 | 应保留的输出及连接 | 怎样定位偏差 |
| --- | --- | --- | --- |
| 图像→点 | 同帧分别取得独立参考点和原模型点 | 原片／帧身份、点顺序、像素坐标、未检出及可定位mask | 肩／肘位置已经错时，先查模型、缩放回映和错人；没有预测也进入覆盖分母 |
| 点→角度 | 对参考点、模型原点、因果滤波点分别用同一动作几何 | 三条角度序列及`value/valid/reason`；参考轴、侧别、起点和时间一致 | 参考点计算仍不符合定义，查几何／机位；原点正确而滤波峰值偏低，查τ及缺口重置 |
| 角度→逐次 | 原状态机和候选状态机消费同一指标序列 | 逐次起点／转折／回位、完整／部分／无法评价、目标及可见质量、cue时刻 | 总次数相同也可能边界错；按事件配对查漏次、重复次、提示提前或迟到 |
| 逐次→评估汇总 | 保存隔离评估，再用原`build_body_profile`读取 | `session_id`、最新状态、范围、覆盖、条件 | 查是否选了同人同侧同来源的最新事实，不用过去最好成绩掩盖当前失败 |
| 汇总→计划 | 复用原`generate_proposal`，不同时改剂量政策 | 原评估指纹、候选／排除原因、目标、规则版本 | 算法输出变化是否意外改变准入、目标或条目选择；计划生成失败也应保存原因 |
| 计划→训练／报告 | 用原保存计划和真实独立反馈走隔离后续链 | `id/revision/entry_key`、执行事实、自评、`blocked/next_key`、报告引用 | 完成、质量、自评和保存分别对账；不能为让对照跑通而默认填无痛或无疲劳 |

已有两段私人录像只具备此前声明的分析授权，不具备自动训练授权；此前v2回放都未确认完整次。它们可以暴露取景／起点问题，不能单独证明计次准确率。独立参考、动作定义和适用条件确定后，才讨论哪个层值得改。具体入口见第24.1节及[参考工作流](development/POSE_REFERENCE_WORKFLOW.md)。

### 27.2 健身与杠铃：人体动作和器械轨迹分开验收

对应F18–F19。固定用户选择的动作、原片、侧别、实际解码时间；人体与器械消费同一录像，但分别保存结果和缺测原因。

| 分支 | 信息传递与算法 | 对照参考／保留产物 | 下游不能反推的内容 |
| --- | --- | --- | --- |
| 人体动作 | 关键点→主关节角→`FitnessEngine`相位→逐次与节奏→所属job报告 | 人工独立动作边界、必要关节点、代理来源与完整／部分计数 | 完整一次不能证明肌肉激活、膝角可见或器械功率可测 |
| 器械位置 | 原帧＋首帧标记→`BarTracker`→原像素轨迹→标尺米制轨迹 | 独立标点轨迹；如团队具备设备，再用对齐时间和测量方向的位移参考。标尺、质量、机位与误差各自记录 | 质量20kg不能提供标尺，也不能修复丢跟；不同平面的参照物不能自动视为同一尺度 |
| 器械导数 | 连续轨迹→局部拟合→速度→满足采样／残差条件的加速度→外力／功率 | 位置、速度、加速度逐层误差；实际采样、残差、边缘及空值 | 看起来平滑不证明导数准确；速度可用不保证加速度或功率可用 |
| 合成报告 | 人体结果＋独立器械结果→job的`result`→历史／回看 | 同一个job和原片身份；各分支覆盖及失败状态 | 不把人体次数与器械上升段强行配成同一事件；不由报告补造轨迹 |

这里的外力／功率只对应既有自由重量竖直模型，不是人体发力真值。可先验证标尺和位置，再验证求导；手机低频人体推理和器械高频跟踪可以作为后续不同采样任务讨论，但当前没有自动统一。源码见[人体分支](../mobile_rehab/fitness.py)、[器械分支](../mobile_rehab/barbell.py)，公式及条件见第9节。

### 27.3 健康、管家与照护：先核对事实，再核对推理

对应F25–F32。用团队明确写下的原句／读数及预期人物、日期、单位、事实状态组成隔离案例；预期语义由独立复核给出，不由同一个理解模型生成答案。

| 层 | 应串起来的信息 | 重点反例 | 判定依据 |
| --- | --- | --- | --- |
| 原输入→接受事实 | 原话／读数→本人或第三人→已发生／否定／假设／不确定→规范事件 | “家人出现症状”“如果发生”“已经没有了”、跨午夜、矛盾时段 | 检查实际事件内容和是否应落库，不只评回复措辞 |
| 事件→日值 | 原事件ID、测次、时间、单位、来源及内容内权限→日数据 | 重复输入、同日更新、血压不同测次、设备来源切换 | 同一事实是否重复；每日取值是否对应原测次；未知是否保留 |
| 日值→变化发现 | 有效日点→基线／近期值→方向差与规则Finding→PersonTwin／解释 | 基线不足、缺日、离群值、来源改变、未发生主诉 | 查看样本数、窗口、规则ID与证据；规则分数不当患病概率 |
| 意图→业务提议 | 既有药物或训练安排→`prepare`→待确认工作流 | 第三人、歧义时间、用量改变、取消或否定 | 不允许提议直接成为完成记录；先核对原记录和操作类型 |
| 确认→实际变化 | 本人／scope／期限／凭证→expected再核对→业务与receipt同事务 | 原事实已改、重复确认、部分失败、响应丢失 | 看实际变化、幂等键和逐步receipt；正确回复不代替提交证据 |
| 已保存事实→家庭／通知 | 获准类别投影→渠道账本→真实送达状态 | 撤权、私密原话、失败渠道、仅本地提示 | 不越权、不假送达；家庭摘要不能扩大原数据权限 |

本机0.20.0的照护语义有已复现缺陷；固定远端0.23.0包含不同保护和确认接入，不能用旧缺陷替它下结论，也不能拿远端源码存在证明本机已更新。先确认宿主和版本，再跑上表。事实血缘还有缺口：`Finding.evidence`并不保证全部是稳定原事件ID，后续可先补离线“事件→日值→规则证据”的映射审计，再考虑统计模型。

### 27.4 居家与安全：事件识别和响应是两套可靠性问题

对应F20–F24、F32。体态需要稳定片段及独立姿态参考；活动、卧室、安全需要完整状态序列、ROI和原始连续时间；支持及通知需要独立业务回执。

| 输出 | 应用什么参考核对 | 算法之后继续追哪里 |
| --- | --- | --- |
| 体态线角／偏移 | 同机位、同定义的独立点与稳定片段；同时检查覆盖、时长和MAD | 体态job、历史条件、指标名称；不扩展为缺少体表点的骨盆前倾或围度结论 |
| 坐站／移动区间 | 人工独立时段标签；区分不可见、坐姿和站姿 | 场景有效时间、久坐任务触发／接受／完成；不可见时间不能当正常活动 |
| 离床事件 | 独立复核床内→床沿→站起→出口的可见序列 | 离床事实与报告；不自动转换为睡眠时长或夜尿记录 |
| 疑似低位事件 | 团队安全获取并授权的正常与异常场景参考；不能要求参与者故意跌倒采样 | OPEN／ACK／RESOLVED、人工支持、获准通知及实际送达；停止相机不代表事件已解决 |

识别侧分别报覆盖、事件漏检、误报次数／可观察小时及边界延迟；响应侧报生成、确认、投递和真实送达的状态／时延。两类指标不能合成一个“报警成功率”掩盖缺口。长期步态疾病风险、全天手机后台、睡眠／夜尿、通话和救援闭环仍不能由当前状态规则自动推出来。

### 27.5 保存与恢复：先查权威事实，再重建派生输出

对应F03、F17、F31–F33及第15节。使用隔离目录和明确所属进程，不操作正常患者库或用户现有服务。

| 情景 | 需要对账的对象 | 正确结果应该满足什么 |
| --- | --- | --- |
| 录像job完成／中断 | 原片、job、`result/error`、康复SQL引用 | 文件与SQL不是总事务；保存成功、作业成功、报告成功逐项说明，缺一项不补“全部成功” |
| v2帧已接收 | session、epoch、seq、接收／处理／丢弃及证据时间 | 接收不等于处理；处理不等于确认完整次；不让暂停前的晚结果污染新状态 |
| v2结束返回202 | 冻结结束操作、`finishing`、后续canonical commit | 202仅表示接收；只有finalized事实与唯一贡献可作为已保存依据 |
| 结束响应丢失／重复提交 | 原操作键、相同载荷、commit与贡献 | 找回同一事实；不同载荷冲突不覆盖原事实，不重复计入计划 |
| 新自评到来／报告失败 | 不变视觉digest、feedback revision、报告对应revision | 自评追加不改次数；旧报告不能覆盖新反馈；报告重建不创造第二份训练 |
| 宿主退出／重开 | 最后检查点、未终结会话、所属worker、恢复commit | 已确认事实保留；未确认部分不得补完整；资源释放与数据恢复分别验收 |
| Care写入后丢响应 | 原业务变化、幂等receipt、工作流各步状态 | 查询原回执，已成功步骤不再执行；部分失败不能冒充全成功 |

此前本机HTTP、TEST几何和特定进程退出验证只覆盖各记录所声明的条件。它们不是目标手机、LAN／TLS、自然弱网、长时运行或突然断电的验收。尤其原HTTP计次失败缺少原时间轴，后来的断流复现没有证明它的原根因；见第16.13节。

### 27.6 现有材料可以验证哪一层

| 当前材料 | 可用的任务／证据 | 尚不能作为哪种真值 |
| --- | --- | --- |
| IRDS Kinect三维骨架及既有标签 | 既有骨架分类研究、固定按人划分、Logistic／TCN基线对照 | 手机RGB二维点、某次真实患者的角度／相位、部署后的临床效果 |

| TEST几何／灰图／白图／故障夹具 | 协议、接口、梯度mask、事务、幂等、资源、可复现故障 | 真人精度、目标手机性能或真实用户轨迹 |

已有两项真实训练结果没有支持候选上线：IRDS TCN未优于Logistic，24段RGB的Ridge／TCN未优于训练分数中位数常量。不要为追求演示效果删困难样本、放宽完成条件或反复用固定test调参。详见第16.2、16.12节及[真实RGB验收](validation/REHAB_MOBIPHYSIO_RGB_2026-10-11.md)。

建议先选第27.1节的一条动作链和第27.5节的一条保存链：前者找最早的测量／阶段偏差，后者确认同一事实可靠落库与消费。两个证据包分别回答“算得对不对”和“有没有可靠传下去”；之后再决定模型、滤波、规则或跨端适配的实施顺序。

### 27.7 文档的证据范围
