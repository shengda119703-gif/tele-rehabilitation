# 安康后端调度：产品逻辑与前端接入

日期：2026-10-10；电脑端版本：0.20.0。医学与路演材料见 [证据说明](ANKANG_MEDICAL_EVIDENCE_2026-10-10.md)，实际验证见 [验收记录](../validation/ANKANG_CARE_2026-10-10.md)。

## 1. 用简单的话解释本轮解决的问题

以前，各模块能完成自己的事情，但助手主要读取康复信息，不能把一条明确的跨模块需求变成可确认、可追踪的操作。本轮增加一个协调层：先核对需求涉及的具体记录，再列出准备做的事，用户确认后交给原模块执行，最后逐项返回结果。

产品主线暂定为：帮助居家康复用户落实已有用药和训练安排，记录执行情况，为后续随访提供依据。首发病种、计划提供者和专业随访角色仍待团队确定。不能从模块数量直接推出医学价值；本项目临床效果目前未知。

## 2. 各模块的职责

| 模块 | 本轮职责 | 实际边界 |
| --- | --- | --- |
| 对话入口 | 识别受支持的明确指令，或继续原健康问答、隐私和安全处理 | 新调度文本是有限规则解析，未引入通用 LLM 动作规划 |
| 协调层 | 准备操作、绑定本人及来源、确认、执行、重试、逐项回执 | 每次最多四项操作，不自行给药或制定临床治疗方案 |
| 用药 | 查询既有安排，记录指定药物／日期／时间的实际状态 | 当前是服药安排和记录，无自动处方、剂量决策或调剂设备 |
| 康复 | 查询原计划下一项，修改既有训练安排的日期／时间 | 不修改动作、组数、次数、角度、计划版本或开始条件 |
| 健康与家庭 | 沿用已有健康记录、历史、授权和摘要流程 | 新照护操作不自动授权家庭、不自动发送外部通知 |

调度顺序取决于具体需求。没有“先给药，再康复，再全部模块”的固定链条，也没有根据药物推断训练禁忌或最佳间隔的规则。

## 3. 为什么当前采用一个入口加明确工作流程

当前业务是固定的记录和安排操作，错误可以通过具体字段与宿主事实发现。多个自主 Agent 不能替代这些业务核对，反而增加协调、延迟和排查工作。

因此采用一个对话入口、确定性协调层、各领域工具。这个工程选择置信水平为中；没有做与多 Agent 的真实用户对照。未来若需要独立研究、复杂文献检索或多个专业角色提出互相审查的建议，再用任务成功率、错误率、延迟与成本验证增益。

## 4. 当前可执行的四类流程

1. **今天安排查询**：读取在用药物的既有时间安排、逐次状态和当前来源的康复日程。未记录保持为未记录，不推断漏服。
2. **康复下一项查询**：桌面使用原 `RehabReadTools` 的计划版本、进度和适用性结果；APK 使用原 `planProgress` 的进度和感受门控。两端原核查能力不同，查询不会自动开始训练。
3. **指定服药记录**：只接受已保存药物和对应发生次数，状态为 `taken`、`skipped` 或 `unrecorded`；未来日期不能预填。更正仍保留原业务审计。
4. **既有训练改期**：保留日程 ID、类型、名称、计划 ID 和版本，仅改日期／时间。确认前已改变药物、该次记录、日程或计划版本时，拒绝用旧提案覆盖。

可将第三与第四类组合为一次需求。例如：

> 记录今天08:00的TEST 药物已服用；今天14:00的训练改到明天16:00。

这段文本要求实际存在对应药物与唯一可定位的日程。原安排与目标日期／时间分开解析。多种药物、多项日程、含糊时间、否定、假设、他人情况、引述或举例会追问。这里是有限表达支持，不代表任意口语理解已经验证。

## 5. 确认、失败和恢复的逻辑

`prepare` 不写入服药事实或修改日程，只保存本人的待确认提案。返回 ID、确认 token、操作明细和十五分钟有效期。确认请求必须包含 `confirmed: true`，且对应当前本人、原来源和使用情境。

协调层按步骤调用原业务模块。宿主将实际业务写入与幂等回执放在同一次提交里；同一执行编号不会重复写入。如果第一项成功、第二项失败，返回 `partially_succeeded`，保留已成功事实，重试仅尝试未完成项。

过期后，宿主仍可返回已经提交的原回执；尚未发生的写入不能沿用旧确认继续执行，需要重新核对并提出新任务。已开始执行的任务不能用取消来撤销真实发生的记录；更正需要走明确的新操作。

清除本人的记录会删除照护工作流和执行凭据，旧 ID 失效。导出审计不带确认 token、原请求签名或执行前的完整事实快照。APK 的备份与恢复剔除可执行工作流和回执凭据，避免恢复旧批准。原业务记录按各宿主已有备份契约处理。

## 6. 前端同学的接入契约

**本轮没有修改前端布局或增加确认按钮。** 后端接口已接通；聊天提案返回 `turn.care.workflow`，原消息文本能展示待确认内容，但单发“确认”不会触发新写入。前端需要增加操作明细和确认／取消入口。

电脑托管手机入口：配对后使用 `POST /api/unified/{operation}?source=LIVE_CAMERA` 或 `source=REPLAY_FILE`。原 cookie 与 `X-Rehab-Client: mobile-v1` 保护沿用；字段不能选择其他 owner 或覆盖 scope。

独立 APK 本地入口：`/api/unified/{operation}` 或 `/api/product/{operation}`。准备、状态、确认、取消用 POST；两项查询也支持 GET。固定绑定当前档案及 `PHONE_LOCAL / SELF_USE`，拒绝档案或来源查询参数。

| 操作 | 请求字段 | 返回 |
| --- | --- | --- |
| `care.overview` | `{}` | 当天指定药物／次数状态与当前来源日程 |
| `care.next` | `{}` | 原计划下一项、版本、可用性与原因、最近训练摘要 |
| `care.prepare` | `requestId` 加 `intents` 或 `text`，二者选一 | 待确认工作流或澄清结果 |
| `care.status` | `id` | 工作流状态；不含确认 token 或请求签名 |
| `care.confirm` | `id`, `confirmationToken`, `confirmed: true` | 各步骤实际回执和总状态 |
| `care.cancel` | 同上 | 未开始的工作流取消结果 |

结构化准备示例（所有 ID 必须来自当前档案实际数据；日期仅为文档示例）：

```json
{
  "requestId": "demo-20261010-001",
  "intents": [
    {"kind": "record_dose", "medId": "med-001", "date": "2026-10-10", "time": "08:00", "status": "taken"},
    {"kind": "reschedule_rehab", "scheduleId": "schedule-001", "date": "2026-10-11", "time": "16:00"}
  ]
}
```

准备返回 `awaiting_confirmation` 后，保留返回的 ID 与 token，确认时发送：

```json
{"id": "返回的工作流ID", "confirmationToken": "返回的确认凭据", "confirmed": true}
```

前端应做到：提案成功与执行成功分别显示；用户核对后才确认；提交中禁用重复点击；超时后先查询状态与业务记录；部分成功逐项显示，不能回退已发生的事实；取消只关闭未执行任务；成功后刷新原日程与用药记录。相同 `requestId` 重发同一需求返回原提案，不同需求不得复用该编号。

待确认凭据不能加到家庭摘要、通知正文或云端共享。私密／不记录对话继续原路径，不创建可执行照护提案。症状、安全提醒、漏服、纠正和分享意图优先沿用原 Runtime；新协调能力没有覆盖这些原处理路径。

## 7. 实现位置

- `ankang/route1-health-agent/src/care/CareCoordinator.ts`：共享流程与有限文本解析。
- `src/product/ProductService.ts`、`src/runtime/session.ts`：本人请求和对话接入。
- `scripts/agent-bridge.cjs`、`app/product/backend.py`、`app/product/care_host.py`：桌面宿主事实读取与工具执行。
- `app/product/daily_store.py`：SQLite 业务事务与持久幂等回执。
- `mobile_rehab/unified.py`：已配对手机接口。
- `android_offline/web/store.js`、`web/local-api.js`：独立 APK 本地事务与入口。

## 8. 已知边界与下一步

现有桌面桥接仍使用一个串行 worker；本轮没有解决外部模型慢响应造成的排队。工作流最多保存 200 条，每个本人执行回执最多 1000 条，达到上限返回错误，不静默删除。后续需要可审计归档策略。

同一协调实例内请求有队列保护，宿主业务提交有幂等回执；多个进程同时操作同一数据目录的工作流登记竞争没有完成验证。当前部署和路演应遵循既有单写入服务架构。

本轮没有新增后台定时提醒、自由 LLM 任务规划、自动训练启动、药物与训练临床联动、诊断、外部家庭通知或专业人员随访服务。旧 APK 安装包 0.2.1 未重打包；新 APK 后端源码已验证，实机与新包仍需后续验收。

路演前优先接入前端确认入口，确定一类真实用户、安排来源与随访提供者，然后用 TEST 数据演示“查询—提案—确认—逐项执行—重查”，加一次信息不明确或第二步失败的演示。临床效果和商业收益按医学证据文档的验证计划分别研究。
