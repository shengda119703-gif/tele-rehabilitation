# 安康照护调度后端黑箱测试报告

本报告检查 0.20.0 新增的照护 Agent 调度：查看今天安排、查询康复下一项、提出服药记录和训练改期、明确确认、取消与失败恢复。完整独立测试 **69 项，59 项通过、10 项失败**。10 个失败来自 **5 种输入分别测试直接提议接口和实际聊天接口**，归为人物归属、时间解析、剂量信息丢失三类缺陷。

**结论及置信度：高。** 明确参数下的执行、确认隔离和恢复路径在本次范围内通过；自然语言入口不能判定为验收通过。确认按钮可以阻止未经确认的写入，但已经实测：用户确认错误提议后，错误内容能够进入业务记录。下一轮应先修这三类问题，再接前端完整确认流程。增加 Agent 数量不能直接解决这次发现的问题。

独立判定标准：明确且受支持的命令可以进入待确认；人物、时间或服药含义不确定时应澄清；准备和聊天均不擅自写入日程／逐次服药；错误凭据和跨用户／来源不能执行；重复确认不得重复记录；部分失败必须如实报告，重试不得重复已完成项。这些标准来自产品行为和输入含义，不以现有实现能做到什么倒推通过标准。

## 人物归属缺陷

**优先级 P1，置信度高。** BB-040、BB-041、BB-054、BB-055。

输入 `张三今天14:00的训练改到16:00` 和 `我朋友今天14:00的训练改到16:00`，预期先核对人物或拒绝修改当前本人。实际两条路径都返回 `awaiting_confirmation`，目标绑定当前 TEST 本人的训练。

在隔离档案明确确认第一句后，返回 `succeeded`，本人 `TEST-schedule` 的时间确实由 14:00 变为 16:00，原计划编号与版本保留。这是**他人语义被错误映射到本人**；跨账号调用本身仍被拦截，不能把它写成跨账号权限泄露。

建议先建立严格的本人命令语法，明确主体必须能被判定为本人；不确定或出现额外人名／关系词就澄清。只增加几个“家人”关键词不能覆盖具名第三人。通过标准应包含当前两句和新的关系／人名表达，且确认前不能生成指向本人业务工具的动作。

补充代码定位：`CareCoordinator.ts` 的 `textIntents` 人物保护和旧理解接口，约 107 行。这是黑箱发现后的定位线索，不替代实际输入输出证据。

## 时间解析缺陷

**优先级 P1，置信度高。** BB-049、BB-050、BB-056、BB-057。

| 实际输入 | 预期 | 实际待确认目标 |
|---|---|---|
| 今天14:00的训练改到上午16:00 | 时段与数字冲突，先澄清 | 当天 16:00 |
| 今天14:00的训练改到中午四点 | 表达含糊，先问具体时刻 | 当天 **04:00** |

第二句在 TEST 档案确认后返回 `succeeded`，保存时间确实为 04:00。不能描述成“只是显示错了”。本次没有执行训练，也没有自动启动摄像头。

建议将日期、时段、小时和分钟分别解析并检查一致性；先验证完整语义，再合成时间。“上午16:00”拒绝猜测；“中午四点”应询问明确的 24 小时时刻，不直接猜成 04:00 或 16:00。新增测试应覆盖凌晨／中午／下午／晚上与数字时间冲突，以及跨日边界。

补充代码定位：`CareCoordinator.ts` 的 `statedTime`，约 80 行。

## 剂量信息丢失缺陷

**优先级 P1，置信度高。** BB-051、BB-058。

输入 `记录今天08:00的TEST 药物 A已服用两倍剂量`，预期识别这是包含异常用量信息的陈述，不能直接缩成普通服药记录。实际提议只显示“已服用”，操作仍为 `daily.dose`、`status=taken`，没有表达“两倍剂量”。

在 TEST 档案确认后返回 `succeeded`，逐次服药保存的是 `status=taken`、`dose=按原说明`。**没有把处方修改为两倍，也没有执行真实给药；问题是逐次记录没有反映用户所述的异常用量。** 对话原文的留存不能代替逐次服药记录的准确性。

建议检测到新增数量、次数或剂量描述时暂停普通已服用记录，先核对实际服用含义，交回合适的原有处理路径。暂不支持记录实际剂量时，应明确说明并澄清，不能悄悄删掉这部分信息。新增测试应包括半片、两片、重复吃一次、两倍和不同单位；本报告不主张让 Agent 自动修改处方。

补充代码定位：`CareCoordinator.ts` 的服药分支，约 126 至 132 行。当前动作字段只表示逐次状态。

## 已通过的关键执行链路

复合操作实际确认后，一次服药记录与一次原训练改期均保存；两个并发 HTTP 确认都得到成功，但服药审计只有一条。原安排编号、计划编号和版本保留。相同 requestId 复用原提议，改变内容则拒绝；已完成工作流再次确认也不增加审计。

部分失败不是伪造工具报错：先准备“记录12:00服药，再把训练改17:00”，随后通过原日程接口新增同计划17:00的冲突安排。确认时服药成功、改期真实失败，返回 `partially_succeeded`；移除冲突后重试成功，已完成服药没有再写一条。

准备后改变药物档案、逐次服药状态或训练安排，原提议均失败并保留新事实。错误确认凭据、confirmed=false、附加 owner 字段、跨来源确认与跨用户拿旧 id／凭据均被拒绝。

重开原服务后，待确认工作流仍可查询。真实发送确认请求后关闭客户端连接，不读取响应，再查询可以核对已提交结果，重试没有重复记录；完成后再次重开和确认同样未重复。这验证了正常重开及客户端丢响应，**没有验证业务提交瞬间强杀进程或断电**。

## 一次数据库异常

2026 年 10 月 10 日 11:00:38 启动的扩展测试，把数据库放在同步工作区的隔离 `qa-output` 中。完成前 58 项后，在确认第三人提议并重新读取快照时，`GET /api/unified` 返回 **HTTP 400，detail 为 `database disk image is malformed`**，测试中断。原始记录保留，不计作完整 69 项运行。

随后把全新 fixture 数据放入本机临时目录，两次完整运行均得到 59 通过、10 失败，没有再次出现该错误。观察证据支持“发生过一次数据库完整性异常”，但**根因未知**：尚未证明由同步软件、SQLite 并发、磁盘或程序哪个因素造成，也不能认为改到临时目录就已修复产品。

建议另做数据库稳定性专项，保存异常文件、检查完整性、定位哪一个存储文件出错，并独立比较同步目录和本机目录。该异常的存在置信度高；归因置信度未知，未验证正式用户库是否受影响。

## 当前功能边界和路演结论

实际聊天可以查安排、生成提议；单独发送 `确认` 返回普通聊天回复，不执行刚才的提议。按照当前接口合同，这不是确认功能失败，但表示**前端确认按钮和完整操作闭环仍未接入**。本次通过接口明确确认，不代表用户在现有页面已经能完整完成同样流程。

尚未覆盖独立 APK 安装包／手机硬件、前端点击和截图验收、外部模型／语音、真实摄像头训练、临床效果、实际十五分钟过期、工作流／回执容量边界、多进程共同写入、长时间压力与瞬时崩溃恢复。下一项查询只验证无可执行评估时不伪造可用状态，没有验证所有病种的康复规则。

现阶段能展示“明确参数的受限调度、确认、记录、查询和异常恢复”。自由聊天涉及上述反例时仍可能误解，路演材料不能声称“任意自然语言都能可靠自动协调医疗服务”。本轮测试没有更改调度业务代码，也没有重打包 APK。

下一轮顺序：先修人物归属、时间冲突与剂量信息处理，保持当前反例的预期值；完成复测后接前端操作卡片，逐项显示对象、日期、时间和状态，再做实际页面验收。数据库异常另列稳定性任务，不能用语言测试通过代替解决。
