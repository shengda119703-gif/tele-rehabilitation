## 3. P1：他人健康数据被写进本人档案

### 最短复现

1. 启动全新隔离 TEST 档案，确认本人指标为空。
2. 经真实 `/api/product/chat` 输入 `张三今天血糖9.5`。
3. 再经 `/api/unified` 读取本人 `state.healthData.measurements`。
4. 关闭并重新启动服务，再读取本人指标。

预期：识别为他人陈述或澄清，不增加本人指标。

实际：增加 `bloodGlucose=9.5 mmol/L`，`source=chat`、`visibility=private`；回复“我已经记下：血糖 9.5mmol/L。这部分只供您本人使用。”重开仍存在。

独立新库还复现：

| 输入 | 实际写入本人 | 重开 |
|---|---|---|
| 张三今天血糖9.5 | bloodGlucose 9.5 | 保留 |
| 李四今天血压180/110 | systolic 180、diastolic 110 | 保留 |
| 我朋友今天血糖9.5 | bloodGlucose 9.5 | 保留 |

`我朋友今天血糖9.5` 在先前已有他人对话上下文的主矩阵中被正确拦截，却在新库误记；因此不能只用顺序对话的通过结果证明主体识别稳定。应按新会话/不同前序上下文交叉验收。

这是语义错误归属，不是跨账号权限攻击：连接仍绑定本人，错误在于把第三人信息转成本人事实。

### 定位线索和修复验收

黑箱完成后只读定位：`ankang/route1-health-agent/src/engine/understanding.ts` 的 `subjectFromText`（138–170 附近）列举亲属后，对含“我”的句子返回 self，无法识别的主体还会继承先前主体或默认 self；没有完整覆盖朋友/具名第三人。`runtime/operationalIntent.ts` 已有较严的操作主体保护，但健康事实写入采用另一套规则。**这是源码支持的原因线索，黑箱结论由实际新增指标和重开证据成立。**

建议：统一事实写入与工具操作的主体边界；具名第三人、朋友、未知主体不可默认本人，先澄清/拒绝本人写入。保留明确本人、真正省略主语的日常表达，但不能靠补几个姓名黑名单验收。修复后覆盖首次空会话、前序本人、前序他人、前序未知及同句多主体；同时证明正常本人记录不被误拦截。

## 4. P1：示例/引用及“不是我的记录”仍被保存

以下各使用一个全新库，均实际持久保存：

| 输入 | 预期 | 实际 |
|---|---|---|
| 资料里写着血压180/110，不是我的记录 | 不增加本人事实 | 本人 systolic 180、diastolic 110 |
| 报告示例中血糖9.5，这不是我的结果 | 不增加本人事实 | 本人 bloodGlucose 9.5 |

前一条回复同时出现“已按您刚才的更正，只处理上一句话对应的事实”与“我已经记下……180/110”。只有回复承认否认/更正并不意味着存储正确。新库与重开读取确认错误事实存在。

只读线索：同文件按分句提取健康值，并识别 `不是我` 为更正标记；完整消息的引用、示例、归属否认尚未可靠约束本条数值写入。建议先判定本条完整归属/引用/否定，再执行事实更正和新增；不能先把引用数值保存，再用末句修补上一条记录。

证据：主矩阵 BB-020；新库复现第 3、4 项。与 P1 他人归属相关，但修复验收需分开，避免姓名保护修好后引用问题仍在。
