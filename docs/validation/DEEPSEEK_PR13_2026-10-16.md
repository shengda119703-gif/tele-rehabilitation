# PR #13：有限真实 DeepSeek 验收（2026-10-16）

结论：**真实模型接通，JSON 格式验证通过；通用语义与最终回复仍为 PARTIAL PASS。** 本轮只测试和审阅，没有修改运行时代码、医学规则或开关，没有部署。

代码基准 `6c1a7771e020526b82dacf2d0185d16577a0cd02`，测试前分支 HEAD `afe63c849c92d2f73eb7b5c00173120574ca3f20`。使用用户本轮授权的 Key，通过关闭回显的标准输入进入临时进程，未将 Key 保存为配置或写入仓库、报告。请求仅发送至现有适配器的 `https://api.deepseek.com/chat/completions`，模型 `deepseek-flash`；设置最多 36 次请求的硬上限，实际 26 次，均收到 HTTP 200。进程已退出，不保留 Key 环境设置。

17 组、19 轮合成输入：18 次真实理解调用、8 次真实最终回答调用。18/18 理解输出通过现有 Schema／原文证据验证；1 轮隐私输入零外发。既有脚本断言 17/17 PASS，但这些断言不足以验证语义和回复质量。不得把脚本的 `real_llm_acceptance: PASS` 等同完整产品验收；证据增加 `overall_manual_acceptance: PARTIAL_PASS` 明确区分。

公共知识检索使用真实仓库资料；本轮个人工具端使用明确标记 SYNTHETIC 的 Mock Host，未读取真实患者数据。上轮实际 SQLite 工具测试仍是另一类证据，不能混称本轮已经用真实模型读取生产个人数据。详见[完整脱敏请求、响应、工具与最终回复](pr13-evidence/real-dialogues-20261016.json)。

| 范围 | 实测结果 |
| --- | --- |
| 普通聊天 | 正确选 chat，未请求工具，生成自然追问 |
| 肩外旋知识、L0/L2说明 | 正确检索公共资料并交给回复模型，保留来源条件 |

| 假设知识咨询 | hypothetical 正确，但错误路由到动作库，最终答非所问 |

| 隐私、工具失败、错用户回执、既有急症处置 | 对应现有自动断言通过 |

**需要修改的语义约定与消费逻辑：**

1. 区分“报告症状”与“咨询一般健康知识”。输入“如果头晕应该注意什么”返回 `route: rehab`、`status: hypothetical`，并调用 `rehab.search_knowledge`，最终要求补充动作名称，明显不对题。建议在 intent 增加一个小枚举 `action: ask | report | correct | query`（名称待实现时统一），让 route 表示领域、action 表示用户行为，并明确普通症状科普不等于动作检索。同时不要在已经明确 hypothetical 时又列“是否是假设”作为缺口。
2. 明确 `mentions[].evidence` 的粒度并调整适配。输入“我今天有点头晕，腿也没劲”，两个 mention 都引用整句，JSON合法，但适配器要求对应旧规则分句，导致“请把每个人的症状……说清楚”的多余澄清。这是协议和消费端不一致，不是模型漏掉症状。应约定能独立支持该症状状态的最小完整原文片段；消费端不能只凭整句／分句字符串不相等就认定主体不清。不需要为此堆更多实体字段。
3. `correction_of` 只表示当前轮明确发起的更正。模型在“说错了，我说的是昨晚头晕，不是今天”之后的“那应该注意什么”仍输出 correction_of。后者只是追问，应通过 mention 的 source_message_id 延续背景，不应再次发出更正标记。更正的当前依据也应与被更正的历史引用区分，不能把历史“我今天头晕”单独当作 negated 的原文依据。

现有 `goal`、`mentions`、`uncertain`、`intents`、`tool_requests` 总体足够，不建议重做大 Schema 或增加未经校准的 confidence。`suggested_tool` 可继续只作旧 v1 兼容，新输出保持 `tool_requests` 为唯一候选列表。上述三项是建议，**本轮尚未实现，也未复测改版 Schema**。

回复体验同样不能宣布全部解决：普通聊天没有例行就医结尾，但“说不清哪里不得劲”等场景仍追加了宽泛急症提示；动作回答存在将候选剂量改写为直接尝试语气的风险，虽然附录保留原许可条件。需要在不改变必要安全规则的前提下单独收紧回答依据和适用条件，不能靠 JSON 格式正确来证明最终回答合格。本轮未作临床正确性验收。
