## 本轮修复

1. `rehab.search_knowledge` / `rehab.search_guidance` 缺少或为空的 query 时，使用当前语义目标、意图、提及和用户原文构造有依据的回退查询；无可用回退查询时仍拒绝。
2. 计划生成强制检索动作知识库和康复指导资料，不因模型漏选关键查询工具而跳过。
3. 若存在本地个人数据读取端，计划生成前强制读取本人当前计划、训练历史和近期评估。个人读取回执仍被过滤出候选生成模型请求，不发送到云端。
4. 若动作搜索没有真实动作卡，停止候选生成，不再让后续 LLM 在空资料上补造动作。
5. 第一层语义 JSON 中若模型生成自引用事件关系，只丢弃无效关系并添加 uncertainty，不再因为一个无用关系拒绝整个用户回合；提示词明确禁止自引用关系。
6. 增加知识动作卡到 App 可执行动作的显式映射白名单。当前仅确认：
   - `T-LOW-003 → knee_extension`
   - `T-LOW-017 → sit_to_stand`
   未映射动作不能被当作可直接写入 App 的计划动作。该映射仅表示技术兼容，不代表医学适用。
7. 增加 Agent CI 工作流，PR 上运行 `npm run ci --prefix ankang/route1-health-agent`，防止新路由代码仅依赖 cloud CI。

## 仍然阻塞的功能

1. **腰椎间盘突出居家训练计划没有经过验证的起始模板。** 不能把普通躯干活动观察或不相关动作强行当成腰突处方。当前应拒绝自动生成可执行计划，直到加入经审查的疾病相关内容、适用条件和明确限制。
2. 候选动作到 App 的映射仍只有两项；多数知识卡不能直接进入患者计划。
3. 候选方案的正式审核/采用流程没有完整贯通。用户确认不能代替必要的专业审核。
4. LLM 候选方案尚未贯通为真实的 App 可执行训练计划（包括动作、侧别、参数、保存 revision、界面刷新）。
5. 健康咨询与 Watch/HealthKit 数据的完整连接仍需按平台与授权实际验证。
6. 真实 DeepSeek 的原 3 组失败需要在新代码上复测；本轮 CI 不包含真实模型密钥调用。
7. 浏览器 UI、Android/iOS 真机和 Apple HealthKit 硬件链路仍未验证。

## 后续补充：通用计划入口（本轮新增）

- 对没有明确疾病/术后限制的通用居家训练计划请求，语义执行层现在返回结构化导航 `automatic_plan`，由产品 UI 打开现有的本地评估驱动候选计划界面。
- 该界面复用现有 `generate_proposal()`、有效评估窗口、个人档案限制、最近训练不适/疲劳门禁、用户适用性确认、计划预览和真实保存逻辑；不会把 LLM 的 `screening_confirmed` 当作授权。
- 对明确的疾病特异性计划请求（例如腰椎间盘突出、术后、骨折、中风、关节置换等），即使路由模型误判为 `health` 或 `other`，也会阻止进入一般活动自动计划界面，说明当前未生成/修改计划，并提示专业核实。
- UI 已增加结构化导航分发，测试覆盖 generic plan intent 的 `automatic_plan` 导航与疾病特异性计划阻断。

边界：这补齐的是**通用活动计划**到既有 App 流程的入口，不代表腰椎间盘突出等疾病特异性处方已实现。疾病特异性计划仍需经过审查的规则/资料、明确适用性审核与相应动作映射后才能开放。
